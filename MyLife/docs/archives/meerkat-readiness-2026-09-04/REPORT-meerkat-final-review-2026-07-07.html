1. Step-by-step: launching the Meerkat pilot

This section records the launch view held on 2026-07-07. The 2026-07-09 audit found additional codeable and critical blockers, so its verdict governs launch decisions. The ordered deploy, secrets, vendor, store, and device-QA steps below remain useful as an operations reference.

Step 0 before anything: the entire pilot lives on feature/meerkat-public-base-feed, which is 98 commits ahead of main and UNPUSHED. Push the branch, merge to main (squash per repo convention), and push main. Everything below assumes the merged tree.
1

Deploy the five services

Required (relay at minimum)
  1. Relay (WebSocket, zero-knowledge): three documented options: Render one-click, Fly.io multi-region, or Docker + Caddy. Fly path: 
    cd packages/meerkat-relay
fly launch --copy-config --config deploy/fly.toml
fly deploy
  2. Community node (port 8890, persists Commons snapshots, serves gated public reads): PORT=8890 pnpm --filter @mylife/meerkat-relay start:community-node
  3. Public directory node (port 8891, discovery): PORT=8891 pnpm --filter @mylife/meerkat-relay start:public-directory-node
  4. Verification service (port 8892, humanity anti-sybil): PORT=8892 pnpm --filter @mylife/meerkat-relay start:verification-service
  5. Persona service (port 8894, alias registry + session tokens; critical for the public layer): PORT=8894 pnpm --filter @mylife/meerkat-relay start:persona-service
  6. Health-check each service (the relay's GET /healthz is what the in-app health gate probes before ever dialing the free default).
Private pilot: deploy the relay only; community/directory/persona/verification nodes are needed only for the public Commons tier. Guide: docs/guides/deploy-a-meerkat-relay.md
2

Secrets and key custody

Required for public tier
  1. Generate the 9 service secrets (session HMAC, admin auth, unlock proof, operator authority, etc.): openssl rand -hex 32 each; set as env vars on the respective services.
  2. Commons operator key (break-glass authority, includes the network-kill seed): generate offline, store offline (hardware key or sealed paper), never in code or CI. It rotates only if compromised.
Private pilot: skip; use dev/test credentials.
3

Provision The Commons

Required for public tier
  1. Run the one-time offline provisioning: generate the operator-signed topic descriptors and serialize to the provision JSON (seal nonces make it non-reproducible, so provision once and keep the file).
  2. Deploy the file to the community node via COMMONS_PROVISION_FILE; the node fail-closes (fatal) on a tampered or invalid file.
  3. Wire the session verifier so gated reads enforce verify-to-view server-side.
Runbook: docs/guides/the-commons-provisioning-runbook.md. Private pilot: skip.
4

Humanity verification vendors

Required for public writes
  1. Cloudflare Turnstile: create site + secret key, set on the verification service.
  2. Apple App Attest: developer credentials + key material for iOS builds.
  3. Google Play Integrity: service account JSON for Android builds.
Private pilot: skip (leave humanity env vars empty; the app fails closed and you verify participants manually).

Required

  4. Pre-build sanity: node apps/meerkat/scripts/check-build-env.mjs, pnpm typecheck, pnpm test, pnpm check:parity --quiet.
Private pilot: development/preview profiles only; distribute via TestFlight internal or EAS internal distribution.

Store setup + the $4.99 unlock

Required for public writes
  1. Create App Store Connect + Play Console app records.
  2. Create the one-time IAP meerkat_app_unlock at $4.99 (founder-locked; wired in packages/entitlements/src/meerkat-app.ts and packages/billing-config).
  3. Set store UGC + 17+ content flags (required because the public tier is user-generated content).
  4. Publish privacy policy + data deletion page (GDPR endpoints are already implemented app-side).
Private pilot: sandbox IAP with TestFlight internal testers is enough; no production store listing needed.

Legal + trust-and-safety operations

Required before public launch
  1. NCMEC reporting vendor onboarding (the CSAM scan + report queue pipeline is built; it needs the vendor account + hash DB).
  2. DMCA registered agent filing; connect the built DMCA intake.
  3. Content moderation policy published; operator console (Plan 39 P12: triage, tombstone, suspend, freeze, kill, append-only audit) staffed.
  4. ECCN 5D992.c encryption self-classification for store export compliance.
Private pilot: skip (known participants, no public UGC surface).

Hosted subscription (optional at pilot)

Optional
  1. Create meerkat_hosted_monthly at $4.99/mo (the only other SKU; storage included) and link RevenueCat.
9

Two-device QA (the gate before inviting anyone)

Required
  1. Verify-to-view: locked Public tab → humanity verify → Commons feed loads real provisioned topics.
  2. App unlock: $4.99 sandbox purchase flips the composer gate.
  3. Public post: compose on device A, dual-signature verify + appear on device B (no optimistic injection).
  4. Private path: pair devices, manual relay session, LAN session (dev build), DM 1:1 + group, file share verify-then-pin, library ingest + sealed playback.
  5. Moderation: report a post, act on it in the operator console, see the tombstone propagate.
  6. GDPR: delete a persona; alias gone, 30-day cooldown enforced.
10

Submit + onboard pilot users

Required
  1. App Store review (24-48h; UGC flags + moderation policy ready from Phase 7), Play review (2-4h), web already live.
  2. Onboard each pilot user: install → onboarding (device identity) → add friend via QR → join your pilot community via invite link → optionally verify + unlock for the public tier.
11

Monitor + operate

Ongoing
  1. Health checks on all 5 services; daily moderation sweep; weekly CSAM queue review.
  2. Known graceful degradation: relay down → LAN/Nearby private mesh still works; persona service down → existing sessions fine, new registrations honestly fail; Commons down → Public tab shows not-available; humanity service down → posting blocked, verified users keep posting.

The private friends-and-family fast path (15-30h)

  • Do: Step 0 (merge), Phase 1 relay only, Phase 5 dev/preview builds + TestFlight internal + web deploy, Phase 9 flows for the private path, Phase 10 onboarding.
  • Skip: Phases 2-4 and 6-8 entirely (no Commons, no humanity vendors, no store listing, no legal ops). The app stays honest: the Public tab simply shows its real "not connected in this build" state.
  • This path gets 5-20 real people syncing communities, DMs, and libraries across their devices with one deployed relay.

2. Current state of the application

Meerkat is a standalone Expo app (apps/meerkat) + web twin (apps/meerkat-web) over the @mylife/sync crypto/node layer and the @mylife/meerkat-relay service package. It is a private, encrypted, device-resident network: communities, channel chat, posts, DMs, sealed file libraries, and (new in Plan 39) a verified public tier. As of 2026-07-07 there is no codeable work left on the launch path; every open plan is blocked exclusively on founder-ops.

What the product is, in one paragraph

A user installs Meerkat and gets a device identity in the OS keychain (no account, no phone number). They add friends by QR/code with TOFU pinning and optional SAS verification, create or join encrypted communities (channels, posts, reactions, files, sealed media libraries with resume-across-devices), and DM 1:1 or in groups with honest signed receipts. Data syncs device-to-device over a transport ladder (relay, LAN, WebRTC, Nearby; BLE wake-only) where the relay only ever sees ciphertext sizes and timing. New in Plan 39: a verified public tier called The Commons, where viewing requires humanity verification (founder NC-2 reversal) and posting requires a registered alias persona (a fresh keypair, never the device key) plus the $4.99 unlock, with dual-signed posts, an operator moderation console, and full CSAM/NCMEC/DMCA/GDPR pipelines behind it. Every claim the UI makes is backed by a real recorded row; the app never fakes connectivity, delivery, or counts.

5. User workflows, step by step

The fifteen journeys that constitute the product, with the screen each step happens on.

1. First run

  1. Launch → onboarding gate onboarding
  2. Pick a device name; privacy statement (zero analytics, E2E, offline-first)
  3. Keys generated into the OS keychain (MK-001 boot order), SQLite created
  4. Land on Feed, empty state pointing to Communities and Messages

2. Add a friend

  1. Messages > + shows your code + QR
  2. Peer scans or pastes the code out-of-band
  3. Both dial the health-gated relay (honest state card if none configured)
  4. Signed identity bundle resolves; TOFU pin
  5. Compare the 16-hex SAS on both screens; confirm → verified friend in People

3. Create a community

  1. Communities > + → Create: name, icon, accent, open/closed template
  2. Owner-signed descriptor written; you are owner; "general" channel auto-created
  3. Gear → Invite → share code/QR/link

4. Join via invite

  1. Tap invite link (or paste in Join) → InvitePreviewSheet
  2. Open community: Join immediately. Closed: Request to join, honest pending state
  3. On approval the descriptor + key handoff sync; channels appear

5. Manual relay sync

  1. Both devices on Sync; same phrase entered
  2. A taps Listen, B taps Sync now; Ed25519 handshake, encrypted session
  3. All in-scope rows exchange; relay sees only ciphertext sizes/timing
  4. Real session lands in history with actual counts

6. LAN sync (dev build)

  1. A: Sync > LAN Listen (advertises via mDNS)
  2. B discovers A, taps it (or types IP:port)
  3. Same handshake over local TCP; session recorded. Expo Go: honest failure, no crash

7. Channel chat, posts, reactions

  1. Community > Channel, Chat | Posts segments
  2. Send text/file/@mention; rows are signed events
  3. Long-press → react / reply / copy / edit / delete (mine) / report (others)
  4. Reaction chips render only verified rows; the local echo is the real recorded row

8. DMs (1:1 and group)

  1. Messages > person > Message, or + for a group
  2. Thread on the chat kit; recipients from the signed group descriptor
  3. Offline peers get sealed mailbox parcels; opened fail-closed on their device
  4. Delivered/read lines only from verified receipts; shred = author-signed delete-for-everyone

9. Share / seal a file + open a link

  1. Share seal → encrypt, Merkle contentId, signed manifest, pin
  2. Share link carries the key; recipient's Open a link checks local pins first
  3. Not local → fetch from pasted hosts + zero-knowledge host discovery, verify-then-pin, fail-closed

10. OS share → Share Inbox → send

  1. OS share sheet → Meerkat stages into device-local intake tables
  2. Share Inbox: pick destination (channel or DM) + caption
  3. Send creates the real message row; label flips Staged → Sent only on the real row

11. Library ingest → playback

  1. Ingest via picker, OS share ("Save to library"), or promote-channel-file
  2. Metadata extracted locally; GPS stripped by default
  3. Sealed under the workspace epoch key; item row curator-signed
  4. Library grid → item → Play/Reader, resume position personal-only

12. Public tier: verify → alias → browse → unlock → post

  1. Public shows the real locked state + $4.99 line
  2. Verify humanity (Turnstile/App Attest) → session issued (spends a humanity token)
  3. persona/create: pick an alias; fresh persona key generated locally
  4. Commons feed unlocks: topics, threads, profiles, all dual-signature verified
  5. Compose passes three real gates (session + humanity + $4.99 unlock); post appears when it propagates

13. Safety: block, report, review, mute

  1. Block from the person sheet or member list (local revocation, send-side filter)
  2. Report any message/post/file → owner review queue Community settings
  3. Public content also reaches the operator console (tombstone/suspend/freeze, audited)
  4. Mute dims a community and silences its unreads

14. Self-hosting / connection server

  1. Me > Advanced connection: the 5-state honest connection card
  2. Enter your own relay URL; all dialing goes through the single health-gated choke point
  3. Free default (if the build ships one) dials only after a real /healthz probe; opt-out honored
  4. Persona/Commons service URLs configure the public tier; unset = honest "not configured"

15. Theming + community identity

  1. Appearance: light/dark, presets, custom axes
  2. Owners set community identity (accent, banner, theme blob), owner-signed and verified at apply
  3. Community themes render only inside that community's screens; high contrast always wins

6. The honesty boundary (the product's spine)

Every surface obeys one rule: no claim without a real recorded row. This is enforced by tests and the cross-surface parity guard, and it is the core differentiator against every competitor's marketing (see the sibling competitor-ads report).

BoundaryRule
Staged ≠ SentShare Inbox shows Sent only when a real message row exists; staging tables never replicate.
No fake presenceNo online dots, no peer counts, no "connected to {friend}". Only recorded sessions appear in history.
Out-of-box connectivityDEFAULT_RELAY_URL defaults to ''; the free default dials only after a real health probe; copy never implies otherwise.
Verify-to-viewThe public gate is enforced server-side; the client mirrors real state (not-configured / locked / needs-session / verified).
No optimistic public postsThe composer never injects into the feed; posts appear when they actually propagate.
Relay blindnessEvery frame crosses in a pairwise envelope; the relay sees sizes and timing only. Dropped negotiation fails the session rather than downgrading.
Delivery truthDM delivered/read lines come only from verified receipts; mailbox opens are fail-closed.
Real counts onlyFeed engagement numbers are counts of verified rows, never client-incremented.
Missing servicesUnconfigured persona/humanity/Commons services produce honest "needs a connection server / not available in this build" copy, parity-locked across surfaces.
Decrypted-export warningsAny playback path that exports plaintext says so explicitly before doing it.
