Meerkat community servers · research, review, and the recommended onboarding design

2026-08-31 · main at 6ed8ce97 · three parallel research passes (Discord mechanics, federated server-choice UX, full code map); the two highest-stakes code claims re-verified directly. Markdown twin is canonical.

Executive summary. Communities today are local by default: they live on member devices, sync peer-to-peer, and joining needs the owner's device online within a short relay-mailbox window. The reframing discovery: the server you need is already in the repo, production-hardened, and orphaned. community-node.ts (2,433 lines) is an always-on node that stores sealed community history it cannot read, with per-member signed auth, rate limits, and roster-revision safety. Around it: hosted multi-tenant tiers with enforced storage caps, Stripe scaffolding, a push gateway, fleet deploy configs, and a desktop self-host panel. But no client ever writes content to it, no community ever gets a host address, and nothing is deployed. The work is wiring plus Discord-grade onboarding, and the shape to copy is Minecraft Realms: one person (the creator) makes one infrastructure choice with a safe default; everyone else only ever sees an invite link.

A2 · Built and waiting, client side

  • refreshCommunityFeed already tries the community node first, with the honest closed source set ('community node' | 'peer' | 'no host reachable' | 'removed'); syncAutomaticCommunityHistory does sealed-registry discovery + atomic history commit on both surfaces.
  • Invites already carry the server address slot: the whole signed descriptor (including hosts and historyScope) rides inside every invite link. Zero wire changes needed.
  • The server path is already SAS-exempt: P2P community sync requires the SAS ceremony; the node path anchors trust in the epoch key + per-message signatures. An intentional affordance for exactly this feature.

A3 · The verified gaps

  1. No writer. Nothing calls the node's publish (with real snapshots) or append. Verified: feed-node-client.ts exports only pullCommunityFeed and a descriptor-only republish used for member removal.
  2. No host address, ever. All six createCommunity call sites (mobile + web) omit hosts; no settings UI adds one; communityNodeUrl() is always null. Verified directly.
  3. Epoch-key custody needs an owner/admin device online. The node holds no keys by design. The one genuine design problem, not a wiring gap.
  4. The join window is a 5-minute in-memory mailbox (24 h max, cleared on relay restart). A handshake straddling a restart is silently lost.
  5. Node self-announcement is a deferred cron, starving the client's working discovery path.
  6. History import is expert-only (paste manifest JSON).
  7. Nothing is deployed; DEFAULT_RELAY_URL = '': a stock build has no out-of-box connectivity.
  8. The app never mints the hosted entitlement bearer; hosted-boundaries.ts admits it honestly (always_on_node: unavailable, "Owner paid").
  9. Identity-rail tension: hosted auth keys off the device identity; Plan 51 walls the account identity away from it.

A4 · Non-negotiable constraints

  • Security lives in the payload; a hosted node is an untrusted transport. No plaintext or epoch keys on any server; the node's roster knowledge is the one bounded exception.
  • Scopes fail closed; cm_publications stays the sole published_blob escalation; every synced table carries id = rowId.
  • Honesty copy: no fake online states, no peer counts, no availability claims without a real reachable host.
  • Plan 51 wall: no account identifier next to a persona or device identifier, anywhere.
  • Pricing founder-locked: app $4.99 one-time, hosted $4.99/mo with storage included. This design invents no prices.

BWhat the ecosystem teaches

B1 · Discord: the experience bar

  • Creation is naming a thing, never provisioning: no region, capacity, or hosting choice; 45+ templates kill blank-canvas paralysis.
  • Invites default to 24 h / 100 uses, editable to permanent; vanity URLs are earned. Critically, an invite survives account creation: a brand-new user lands inside the server after in-line signup with no separate accept step.
  • Onboarding is a funnel: rules screening → customization questions doubling as role picker + channel opt-in → curated 3-5 channel default view → first-task checklist. Practitioner consensus: the full channel wall at join is the top driver of joined-but-never-posted.
  • Discovery is an earned, continuously re-verified status (1,000+ members, 8+ weeks, activity re-checked), which prevents directory rot.

B2 · Federated cautionary tales

  • Mastodon is the on-record proof that server-choice-first onboarding kills conversion: in 2023 it demoted the picker below a one-tap default; Rochko said users "bounce and never hear from them again" before experiencing the product.
  • Matrix/Element: pre-filled default plus Element Home ("your own server, zero ops") as the paid upgrade path. Same pattern at masto.host and PikaPods: self-hosting is the upgrade, never the entry.
  • Bluesky decoupled identity from infrastructure: everyone lands on the default PDS; the fun choice is a vanity domain handle, changeable any time. Meerkat already has this right (identity is a device keypair, not a server name); keep servers out of every identity string.
  • Nostr converged on hardcoded default relay lists despite maximalist ideology; Farcaster shows you can hide a resource's cost when you cannot hide the resource, and that fixing one leaky layer exposes the next (watch that pairing/friend codes do not become the new choose-your-server moment).
  • Mastodon's lossy migrations teach users to distrust defaults. Meerkat's community exit is already cleaner; say so in the UI.
B3 · Minecraft Realms is the exact shape to copy. Official managed hosting for a normally self-hostable game: the owner pays, invited players pay nothing and never see server config, and joining is an invite link or code redeemed in the client. One person's infrastructure decision covers the whole group. That is a Meerkat community with a hosted node.

B4 · Distilled design rules

  1. Default to working infrastructure; never a server picker on the happy path.
  2. Only the creator ever sees an infrastructure choice, once, with a safe default and a secondary escape hatch.
  3. Keep the server out of identity: names, friend codes, handles never contain a host.
  4. The invite link is the entire onboarding surface for everyone else; it must survive install and account setup.
  5. Self-hosting is the power-user upgrade (the desktop panel is built for this), not the entry gate.
  6. Portability is a stated promise, backed by the already-built community exit.
  7. Curate the first session: templates, small default channel set, first-task guidance.
  8. Discoverability is earned and re-verified, not a one-time listing.
  9. Where honesty forbids hiding a state, show the true state in plain words.

CRecommended design

Working user-facing name for the always-on node: the Keeper. "A Keeper is a server that keeps your community available while everyone's phones are asleep. It stores only sealed data it cannot read." (Naming is a suggestion; mechanics below do not depend on it.)

C1 · The one decision card (creation flow)

1 · Meerkat Keeper (recommended)One tap, provisioned instantly on the hosted service under the existing hosted plan ($4.99/mo, storage included; tier caps already enforced server-side). Copy states plainly what the server can and cannot see.
2 · Run your ownHands off to the existing desktop panel / compose deploy; the app accepts the panel's verified connection card, powered by the already-built off-host reachability honesty.
3 · Just our devices (default)Today's behavior with today's honest copy: "Available from members who have it, when a sync connects."

Reversible in a new "Community server" settings section (add host = descriptor revision; remove = the already-designed community exit). Non-creators never see any of this.

C2 · Invites become the whole onboarding

  • The descriptor rides inside the invite, so once hosts is populated every invite automatically carries the server address.
  • Preview sheet gains an honest availability line; invite controls grow Discord-grade TTL + max-use caps + revocation; permanent invites are offered only when a Keeper is attached (a permanent invite to an unhosted community would be a lie half the time).
  • New-user funnel: tap link → install/web → invite fragment survives first-run (deferred deep link) → age gate → preview → join → rules screening → land in the template's default channels with a 3-item first-task guide.

C3 · The asleep-owner problem (the one hard decision)

  1. Baseline, always: durable join queue + push wake. Move join requests from the 5-minute in-memory mailbox to a durable, restart-surviving queue on the community node (it legitimately knows the roster and now has Postgres). The push gateway wakes owner/admin devices; the grant flows over the existing handshake. Joiner copy: "Your request is waiting for an organizer's device."
  2. Delegation: admins can grant. Admin inviters are already validated; extend grant-minting to admin devices so multi-admin communities answer in minutes. Pure key custody, much better latency.
  3. Owner opt-in per invite: instant-join links. An invite variant embedding a key-wrap to an ephemeral invite key: the link itself is a bearer read capability, scoped by historyScope (default join_point), TTL-bound, use-capped, revocable by epoch rotation. Toggle copy: "Anyone who gets this link can read the community without waiting for approval." The Realms code, expressed in Meerkat's sealing model. Opt-in, never the default.

C6 · What not to build

  • No server-side epoch keys outside the explicit per-invite instant-join consent. No plaintext server-side, ever.
  • No online-member counts or green dots from the node, even though it could technically count connections.
  • No new prices; the hosted plan is $4.99/mo with storage included, full stop.
  • No server name in any identity string, friend code, or handle.

DFounder dependencies and open decisions

  1. Fleet provisioning gates everything (W5): deploy the community node + hosted service, set the default relay URL in builds, run the announce cron. Plan 44's founder-ops evidence list applies.
  2. Billing wiring (W3): Stripe live keys; decide iOS in-app purchasability vs web-only for the hosted community plan.
  3. Decide on instant-join links (C3.3): recommended as owner opt-in; the durable queue + admin delegation alone already beats today's five-minute window by orders of magnitude.
  4. Naming: "Keeper" vs plain "community server" in user copy.
