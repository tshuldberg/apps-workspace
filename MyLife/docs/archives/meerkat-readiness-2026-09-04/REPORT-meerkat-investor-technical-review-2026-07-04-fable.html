1Executive summary

Meerkat is a privacy-first social network where the cryptography, not the company, is the trust layer. Every message, post, file, and community is created, sealed, and signed on the user's device. Servers in the system are deliberately blind: the relay forwards ciphertext addressed by ephemeral tokens and can see only sizes and timing. There is no account database to breach, no feed algorithm to manipulate, and no advertising surface to sell.

2What Meerkat is

Meerkat looks like a modern community app: a feed, communities with channels, posts with threads and reactions, direct messages, and file sharing. Underneath, it is a local encrypted node.

The user experience

  • Feed: a content-first home screen assembled locally and explainably from your communities: posts, replies, mentions, unread highlights, and files. No engagement algorithm, no injected content, deterministic controls.
  • Communities: create or join with an invite code or QR. Each community has channels (chat and long-form posts), a files index, member profiles with signed avatars, roles, and owner moderation tools.
  • Messages: one-to-one and group DMs with honest delivery states. "Delivered" and "read" render only from cryptographically verified receipts, never from optimistic guesses. Includes block, report, disappearing messages, and author-signed delete-for-everyone.
  • Friends: pairing by friend code or QR with safety-number (SAS) verification, trust-on-first-use key pinning, and local revocation.
  • Publishing: a community can publish selected channels to a public, anonymously readable layer with owner-signed rights and takedown, serving readers without exposing member identities.
  • Self-hosting: any user can point Meerkat at their own connection server. A desktop host companion provides a wizard and dashboard for running an always-on community node.

The three-sentence technical identity

Every device generates its own Ed25519 identity in the OS keychain, and all content is sealed and signed on-device before anything leaves it. Devices sync directly over LAN, WebRTC, or nearby-radio rungs, or through a zero-knowledge relay that forwards opaque frames addressed by per-session ephemeral tokens. The company's servers cannot read messages, cannot enumerate members, and cannot even see message types or timestamps inside a session.

Positioning in one line Signal's security model, Discord's community shape, Mastodon's independence, and Apple's design discipline, in one $4.99 product.

Unit economics sketch

The relay forwards opaque frames and stores only parked ciphertext envelopes until drain; it keeps no accounts, content, or graph. Comparable stateless WebSocket relay workloads run well under $0.10 per active user-month at scale, and the community node is a bounded, capped process (state bounding shipped in the current branch). Even with the included hosted storage at typical utilization (paid cloud-storage users rarely exceed 25 to 35% of their allowance), blended COGS per subscriber projects in the $0.60 to $1.20 range, supporting healthy gross margin at $4.99, protected by fair-use allowances set from real provider invoices and by peer-first bandwidth. Zero ad-tech, zero content moderation at the server (the server cannot read content; moderation is community-level and user-level by design) keeps opex structurally lower than readable-content platforms.

Revenue expansion path Every subscriber also bought the app, so each hosted user is worth $4.99 once plus $4.99/mo, with no acquisition spend beyond the invite graph. Beyond that: a hosted community-node offering for larger organizations picking up the orphaned Workplace long tail, and Meerkat as the network substrate for the wider MyLife suite (40 modules sharing the same sync engine), where every module is a $4.99 unlock in the existing billing config.

7Technical audit: architecture

Meerkat is three deployable pieces over one shared cryptographic engine. The app owns no cryptography; every primitive lives in the audited @mylife/sync package and is consumed identically by mobile and web.

+---------------------------+ +---------------------------+ | Mobile app (Expo/RN) | | Web app (Next.js) | | iOS + Android | | sql.js + OPFS/IndexedDB | | expo-sqlite + keychain | | WebCrypto secret store | +------------+--------------+ +--------------+------------+ | both consume @mylife/sync | v UNCHANGED (adapters only) v +---------------------------------------------------------------+ | @mylife/sync: the node layer (1,559 tests) | | identity (Ed25519, keychain) sealed shares + share links | | Noise handshake w/ transcript signed batches + HLC merge | | binding + per-msg ratchet group keys + epoch rotation | | TOFU pinning + SAS verify zero-knowledge mailbox | | frame envelopes (metadata host registry (opaque HKDF | | hidden from relay) ids, secretboxed records) | +-------------------------------+-------------------------------+ | transport ladder (ranked, capability-probed) LAN TCP+mDNS | WebRTC | Nearby | BLE (wake-only) | Relay | v +---------------------------------------------------------------+ | Relay + community node (@mylife/meerkat-relay, 325 tests) | | - WebSocket relay: forwards ciphertext frames addressed by | | per-session ephemeral tokens; sees sizes + timing ONLY | | - Mailbox: parks sealed envelopes for offline devices | | - Community node: always-on seeder, public directory, | | per-IP DoS limiter, capped/bounded state | +---------------------------------------------------------------+

Key architectural decisions an auditor should note

  • Single crypto source of truth. The apps import identity, sealing, pairing, sync, mailbox, and publishing primitives from @mylife/sync. The web client reuses the package unchanged behind three browser storage adapters. There is no duplicated or app-local cryptography to drift.
  • Scoped data model, fail-closed. Every synced entity declares a scope (device_local, personal_replica, shared_workspace, published_blob) with per-entity maxScope caps. After a 2026 audit finding, the community policy default flipped to device_local: a table omitted from the rules fails closed and syncs nothing. A guard test asserts no table can be created rule-less. Exactly one table (cm_publications) may ever escalate to public.
  • Read models are verified models. Reactions, profiles, delivery states, and public pages render only from signature-verified, safety-filtered read models. A malicious or malformed event is dropped and counted, never displayed.
  • Deterministic merge. Hybrid logical clocks plus OR-set semantics give convergent state across devices without a coordinating server; conflicts requiring human judgment surface through explicit resolvers rather than silent last-write-wins.
  • Storage split. Metadata and indexes live in SQLite (per-platform adapters); sealed ciphertext blocks are content-addressed files verified against their manifest on every fetch (verify-then-pin, from any host, trust never delegated to the host).
  • Bounded servers. The relay and community node carry per-IP DoS limiters, durable capped stores, and state bounding, so a hostile client cannot balloon server memory or disk.

9The honesty boundary: an engineering differentiator

Meerkat's most unusual property is a codified rule that the UI is never allowed to claim more than the network is really doing, and the rule is enforced by tests, not policy documents.

  • The "What works today" screen derives from a single typed capability list whose statuses are computed from the real feature flags and substrate. An entry cannot say "live" while its flag is off; the compiler and tests forbid it.
  • Connection status renders one of five states driven by a real health probe of a real server. No state string is a fake peer count, an online dot, or a fabricated "connected to friend" claim.
  • "Sent" appears only when a real message row exists; "delivered" and "read" only from cryptographically verified receipts; a staged OS share is never described as sent.
  • A build with no configured default server ships with no out-of-box connectivity and says so plainly, guiding users to same-Wi-Fi pairing or their own server.
  • Simulated transport backends exist for testing and are structurally barred from presenting as live rungs; a WebRTC session reports connected only after a real ICE negotiation completes.

Why this matters to investors: the graveyard of decentralized social is full of products that demoed a network they had not built. Meerkat's discipline means every demo is real, every claim in this document maps to shipping code, and the trust brand ("we cannot read your data, and we do not lie about what works") is defensible under hostile technical scrutiny, which is precisely the scrutiny privacy products attract.

11Why Meerkat wins

  1. Structural cost advantage. Blind servers are cheap servers. No content moderation infrastructure at the server (it cannot read content), no recommendation compute, no ad stack, peer-first bandwidth. The $4.99 price is sustainable for Meerkat and ruinous for readable-content incumbents to match.
  2. Trust that compounds. Every breach headline, every platform ad-policy reversal, every subpoena story is organic marketing for a product that provably cannot comply with data demands it never possesses the keys to satisfy.
  3. The invite graph is the growth engine. Communities onboard their own members; a single club owner converts dozens of users. Friend-code pairing and QR joins make the loop native to the product rather than bolted on.
  4. Suite leverage. Meerkat's sync engine is the substrate of the 40-module MyLife suite. Every module shipped enlarges the network's utility and the subscriber base sharing the same infrastructure cost, a portfolio dynamic no standalone messenger has.
  5. Honesty as brand. The enforced honesty boundary converts the product's engineering culture into a public, verifiable differentiator in the one market segment (privacy) where users actively audit vendors.
  6. Timing. Workplace's June 2026 shutdown, Bluesky-proven migration appetite, and normalized paid-social pricing open a window that did not exist two years ago.
