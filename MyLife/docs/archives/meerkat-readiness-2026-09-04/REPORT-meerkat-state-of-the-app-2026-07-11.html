Exact current state

NO-GO for public release. This has not changed since the 2026-07-09 Blackglass adversarial audit (docs/reports/REPORT-meerkat-blackglass-production-adversarial-audit-2026-07-09.md). The audit scored actual public release readiness at 63/100 even though the already-implemented code paths scored 86/100 and security controls in those paths scored 88/100. The gap is deliberate: a production release requires the product, its infrastructure, its third parties, its policies, its operators, its backups, and its physical-device behavior together, and most of those are not yet true.

Since the audit, all of the audit's follow-on plans (42, 43, 44) have had their codeable scope substantially completed and merged or in-flight, but every remaining blocker that requires live infrastructure, provider credentials, physical devices, or human operations is still open. Nothing in the current tree changes the release decision.

Known tech debt specific to Meerkat

From memory.md "Known Tech Debt" (2026-07-11) and direct verification:

  • Meerkat launch-hard code remains split across Plans 25 (calls/rooms, not started), 41 (storage destinations, not started), 42 (native transport, codeable done / hardware pending), 43 (managed archive/safety, codeable substantially done on branch / not merged). Plan 40 owns Share Inbox DM routing, exported stub removal (SignalingClient, PushRelayClient legacy stub, TrackerClient, PaidContentManager), and stale-truth reconciliation across docs/UI/store copy.
  • Production stateful services still require live cutover, HA, PITR, restore drills, observability, and release-governance evidence; "live community bin test tier needs CI-provisioned LOGIN role URLs."
  • Push-gateway loadRegistration is O(n): confirmed in code at packages/meerkat-relay/src/push-gateway.ts:602-613. It paginates through listRegistrations in pages of 200 (capped at 10,000 iterations = 2,000,000 records) doing a linear scan for a hash match, because "no by-id getter exists" on the store interface. The code comment documents this as a known limitation; needs a getRegistration(idHash) store method. Not a correctness bug, a scale bottleneck.
  • @types/react remains out of sync with Expo expectations; RN package/resolver drift can cause duplicate native runtimes.
  • Native transport source (Swift/Kotlin) is authored but has never compiled in a real dev/EAS build or run on physical hardware — every AC-42.1/2/3/7/9/11 item is HARDWARE-GATED per the status ledger, and a .gitignore defect that would have silently shipped the native package empty was only caught by direct review during Plan 42, which is a live signal that "authored" and "verified working" are not the same claim for this codebase.

Executive summary

Meerkat remains NO-GO for public release, unchanged since the 2026-07-09 Blackglass adversarial audit which scored actual release readiness at 63/100. All seven original critical defects and the full independent 12-finding challenge pass from that audit are closed and evidenced (4,397/4,397 Meerkat tests passing at the remediation commit). Since the audit, Plan 42 (native transport, push, background lifecycle) had its entire codeable scope completed and merged: real APNs/FCM/Web Push provider adapters, an owned Swift/Kotlin native transport package, and self-testing static honesty gates — but every native-transport and push claim stays explicitly HARDWARE-GATED because no code has run on physical devices. Plan 43 (managed archive, NCMEC/DMCA, automatic history sync) has all four work packages landed on branch feature/meerkat-plan43 (12 commits ahead of main, not yet merged), with active uncommitted follow-on work in packages/sync. Plan 44 (PostgreSQL, object storage, backup/restore, signed release supply chain) reports all eight phases codeable-complete, leaving only founder-operated evidence: a first signed pipeline run, live restore drills, a 48-hour soak, and 10x load tests. Plans 25 (calls/rooms) and 41 (storage destinations) remain fully unstarted, both explicit hard stops per Plan 40's launch gate. Monetization is genuinely wired, not stubbed: RevenueCat SDK on mobile, signed server grants on web, and a real dependency-free Stripe REST/webhook client on the relay, none of it has processed a live transaction. The one confirmed piece of technical debt worth flagging beyond docs: push-gateway.ts's loadRegistration does an O(n) paginated scan (capped at 2M records) because the store lacks a by-hash getter. Bottom line: code readiness is high and improving fast, but release readiness is gated on infrastructure provisioning, physical-device proof, live provider credentials, and human safety/legal operations that no amount of additional code can substitute for.
