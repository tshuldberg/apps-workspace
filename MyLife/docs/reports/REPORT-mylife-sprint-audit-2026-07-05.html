2. Meerkat: DMs and launch execution (Plans 19, 21, 23, 28)

Why
Plan 21 (full direct messages) was rated the single largest functional gap before paid launch: the app showed an honest "DMs unavailable" dead end. The founder's launch definition requires E2EE 1:1 and group DMs with honest signed-proof receipts, at mobile/web parity, built by extending @mylife/sync with zero new crypto. Plans 19 (public social layer), 23 D.6 (Noise transcript binding), and 28 (real member removal, replacing a fake rotation path) close the remaining trust-layer launch blockers.

What was built

  • Group DM engine: dm-group.ts descriptors reusing group-keys verbatim, epoch-backed key handoff (dm-group-handoff-core.ts), forward secrecy on removal proven by a 3-engine live-relay e2e (a removed device cannot read epoch N+1).
  • DM provider on both apps: send/drain with honest delivery (parked only on a real relay park, delivered/read only from a verified receipt), attachments with verify-then-pin fail-closed, author-signed delete-for-everyone (dm-shred.ts with a two-layer author guard), block as real key revocation.
  • Member removal (Plan 28): owner-signed removal revisions, epoch rotation, survivor mailbox fanout. This replaced code paths that previously could not truly remove anyone.
  • A bootstrap FF3-class trap caught in review: a new group member cannot derive the commit mailbox token until it has the conversation it only learns from the commit. The fix parks each handoff on the member's pair-private token as a bootstrap channel. This class of bug (a mailbox token nobody polls = silent non-delivery) was caught three separate times this sprint by closing reviews.

Codex audit (packages/sync) 7/10

Mitigation: epoch rotation still denies the removed device new content keys, so this is an authorization-bookkeeping gap, not a confidentiality break.

3. Meerkat: UX parity rebuild (Plans 30, 31, 32)

Why
Benchmarking scored the core chat loop 4.5/10 and the Feed 3/10 against Discord/Slack/Reddit grammar. The engine was honest and sound; the surfaces read like an engineering dashboard. Founder sequencing: functional plans first, then the UX set, with Plan 30's chat kit landing right before Plan 21's DM UI so DMs shipped on the new kit from day one.

What was built

  • Plan 30, chat rebuild: a shared props-only chat kit (both palettes), inverted virtualized message list, grouped bubbles, reactions, replies, @mentions, a focused live loop with a new-messages divider, auto-drain replacing the manual Refresh button. Web got a full twin (chat-compose.ts and the m3 loop).
  • Plan 31, navigation and join: five-tab IA (Friends merged into Messages), Communities became a navigation surface instead of an admin console, and joining collapsed into one pipeline with four doors (link, QR, code, nearby) plus onboarding v2 and a capability-honesty page that plainly states what works without a relay.
  • Plan 32, content-first feed: feed cards with inline media, reply counts, reactions, real signed image avatars, and sender-generated link previews (receiver never fetches, an explicit metadata-privacy decision). Explainability moved behind an info tap instead of dominating the surface.

Codex audit (Meerkat apps + relay) 7/10

HIGHVERIFIED
packages/meerkat-relay/src/community-node.ts:168
FileCommunityDescriptorStore.recordRevision uses plain fs.writeFile for the restart-safety revision file. A torn write makes getHighestRevision return null after restart, which would let an older owner-signed roster be replayed. One-line fix: use the existing atomicWriteFile helper.
HIGHVERIFIED (design limitation)
apps/meerkat/app/(root)/data/link-preview.ts:120
The sender-side SSRF guard blocks literal private IPs and redirects but cannot defend DNS rebinding: a public hostname resolving to 192.168.1.1 or a metadata IP will still be fetched on the sender's device. Impact is bounded (the fetch runs on the sender's own network, not a server), but worth a resolve-then-pin check where the platform allows it.
MEDVERIFIED with nuance
apps/meerkat/app/(root)/providers/ChatProvider.tsx:181
Channel sends swallow mailbox fanout failure (.catch(() => undefined)) and reconcile the pending bubble once the message commits locally. In a local-first design "committed + queued" is a defensible sent-state, but if the fanout path has no durable retry a total relay failure becomes silent non-delivery presented as success. Recommend verifying the queue is durable or downgrading the bubble state.
MED
apps/meerkat/app/(root)/data/loopback-server-core.ts:115
parsePlaybackPath calls decodeURIComponent unguarded; malformed percent-encoding throws before the bounded 400/404 path.

Why
Plan 37 is a sequencing map, not new specs: it orchestrates every remaining codeable gap between main and the founder-locked launch definition ($4.99 one-time app, free anonymous public viewing, everything ships together), superseding the stale July 1 orchestration doc. It was authored from the 2026-07-04 production audit and explicitly carries the EAS blocker (Metro rejecting the dynamic native-module require in ble-backend.ts).

What was built (commit aaa8bace + Wave 1 foundations)

5. Meerkat: Plan 38 media library ("private Plex")

Why
Founder direction (2026-07-04): users should be able to organize and retheme any of their communities, and optionally run one as a Plex-style personal media hub. Every community is already an encrypted, membership-gated blob store; what was missing was the metadata/browse/playback UX. The plan was Codex-reviewed before execution (10 binding amendments folded in, including D.3 epoch-wrapped per-object DEKs), then executed in one day across both surfaces with zero new crypto.

What was built (27 commits, Phases 0-7 + C.1-C.10)

  • Phase 0 engine: library DDL and scope rules, sealed-object transfer leg, library-object sealing with epoch-wrapped per-object DEKs, apply-time validator seam for owner-signed rows, two-node e2e.
  • Phases 1-2, Track A: community identity and retheme (owner-signed identity rows with leakage tests, in-row icons, sealed-object banners), organization (categories, archived read-only channels, W2 channel-creation fix), organized descriptor revisions gossiping to members.
  • Phases 3-7, Track B: library substrate data layer, metadata pipeline and enrichment, personal "My Library" hub, ingest UI, sealed playback via a loopback range-server pure core (D.5) with expo-video on mobile and web twins, music queue, templates, library-first layout, theme share/adopt, full storage model with budgets.
  • C.6/C.10: photo timeline + offline map with checksum-verified tile packs, per-community notification identity behind a dev-build flag.
  • Final state: sync 1,692 / relay 347 / mobile 953 / web 643+ tests green, 6 DDL twin locks and 40+ parity-locked strings. Remaining work is founder-ops only (dev builds, 2-device QA, tile hosting).

Codex findings that touch this workstream: the deferred apply-time signature enforcement for cm_library_items (known seam, section 2) and the unguarded decodeURIComponent in the loopback parser (section 3).

6. BestChef: Plan 33 global launch (7+ languages)

Why
BestChef is the suite's first true public consumer launch; its concept scored 8.5/10 in two evals, so the risk is not product-market fit but the missing floor of trust-and-safety, localization, and operational truth. The 2026-07-03 adversarial review confirmed 15 blockers and added 17 defects, several press-visible in week one (English hardcoded into backend SQL notifications, slugify breaking non-Latin dish creation, no fonts loaded, an untranslated compliance block in every non-Latin catalog). Plan 33 takes it from English-only TestFlight build 24 toward GA in en/es/pt-BR/fr/de/it/ja across 14 storefronts.

What was built (53 commits, Phases 0-5.6)

  • Moderator console (apps/bestchef-console): a new allowlisted Supabase-auth app for reports, appeals, proof queues, dish translations, media approval, and a submission-video promotion queue feeding the public feed end to end, including appeal reversals re-publishing restored videos.
  • Integrity floor: durable per-action quotas, a global vote-proof hash ledger (kills the free delete-and-revote loop), server-side blocks, and machine error codes from every edge function so the client can localize errors instead of piping raw English.
  • Localization for real: dish translation layer with locale-aware search RPC, UGC language tagging (columns, queue-stamp trigger, feed/leaderboard filters, epoch-guarded Vote language pill), the ~105-key compliance block translated across 20 locales, backend notifications converted to type+params (no stored English), CLDR plural categories, localized times, an RTL mirrored-icon pass, and multilingual dish emoji keyword maps. Roughly 978 keys x21 catalogs, guarded by new raw-string and rtl-icon parity gates.
  • Media pipeline: server-mediated upload/finalize, a durable mobile upload queue (the merge gate later caught and fixed its same-millisecond FIFO tie), a TS-04 purge worker, and a pending-submission sweeper.
  • Legal + UX: legal corpus with per-country age gates and a DSA appeal flow, error states, cold-start CTAs, Dynamic Type clamps, AA contrast, video comments (F-008) and cloud bookmarks (F-010) closing two reopened tickets, trophy moments, and an honest completeness threshold.

Codex audit 7/10

HIGHVERIFIED NEW
apps/dowork/app/(root)/data/cloud-shares.ts:289 and cloud-coaching.ts:623

12. Bottom line

The sprint was real, and the discipline held. 234 commits in four days across four products, and both models land on the same read: the engineering pattern is consistently honest (fail-closed parsing, signed rows, verified-only read models, no fabricated connectivity), test discipline is unusually strong at the crypto and protocol boundaries (240 new test files; sync at 1,692 tests), and the merge gates caught real bugs that individual branches missed three separate times.

Cross-model verdict spread is tight: Codex scored the six areas 6.5-7/10, and my verification pass confirmed every HIGH it raised (two turned out to be already-tracked seams rather than surprises). No finding was refuted outright; one (ChatProvider send state) softened with local-first nuance.

What actually needs doing next, in order:

  1. DoWork queue classification (finding 2): two-line class of fix, directly user-facing, and DoWork is the closest product to GO. Pair it with the already-logged START-dispatch defect.
  2. Sync removal convergence (findings 1, 8): fold roster reconciliation into descriptor apply and extend channel-post gating to device-scoped sessions. Both belong in Plan 37's remaining waves.
  3. Meerkat relay atomic write (finding 4): one-line fix with the existing helper.
  4. MyNews createNewsroom RPC (finding 3): make it atomic before founder-ops provisions the backend.
  5. BestChef worker claiming + job health merge (finding 9): fix before the moderation queue sees real volume; the classifier stub (finding 7) stays the launch gate it already was.

None of these change the portfolio ruling: the products are blocked on commercial shell (billing, deployment, legal, trust-and-safety vendors), not on this sprint's code. The sprint moved four products from "engine" to "product" in four days; the findings above are the punch list that keeps the honesty bar intact.
