State summary

DoWork is a $4.99 workout tracker with an invite-only trainer platform: trainers publish demo videos and a public profile, run a private form-check coaching loop with clients, and earn through an 8-tier subscription ladder. The app is local-first (single SQLite dowork.db, 18 wk_* tables, 6 migrations via @mylife/workouts) with Supabase for auth, the trainer directory, the signed video pipeline, purchases ledger, and push. Plan 46 (2026-07-11) closed every code-addressable audit finding; the 2026-07-04 wave had already landed monetization (RevenueCat wrapper with server-truth confirmation), launch hardening (push, deep links, offline downloads with entitlement re-checks), and the audit's honesty fixes (paid-through cancellation, ended-link read-only, honest offline queues). Live sessions boot in the playing state so sets are always loggable (fdf942ea), and the orphaned hub calculator was retired for parity in b317711a.

1Entry, Onboarding & Account

The onboarding and account workflow in DoWork is a genuinely local-first, honesty-first implementation rather than a stub. Entry routing and onboarding write only to local SQLite (hub_settings) with no network dependency, so a first launch never blocks on connectivity. Once the user touches identity (account.tsx, auth-callback, reset-password, redeem-invite, notification-preferences, blocked-users) every screen talks to a real Supabase backend with distinct, hand-written states for loading, empty, error, and success rather than generic spinners or silent failures, and destructive or identity-changing actions (sign out while anonymous, delete account, redeeming a trainer invite while anonymous) get explicit confirmation or blocking copy instead of proceeding quietly.

Auth Callback (loading state) app/(root)/auth-callback.tsx

Deep-link handler for dowork://auth-callback from Supabase magic-link and password-recovery emails (the client runs with detectSessionInUrl: false, so this screen does the exchange manually). It reads the fragment tokens from the raw linking URL (preferred, since #access_token never reaches router params) or falls back to query params, calls completeAuthCallback, refreshes cloud identity, then routes to reset-password (recovery) or the tabs (sign-in). Waits for either a URL or params before acting rather than flashing a false error on first mount.

  • Loading (shown): ActivityIndicator + "Finishing sign-in…" while the exchange runs
  • Error state: "Sign-in link problem" title + specific error body (e.g. "Cloud is not configured on this build") with a "Back to sign in" button routing to /account
  • No success UI is shown because success immediately navigates away

Settings Tab app/(root)/(tabs)/settings.tsx

The largest screen in the app: Account, App, conditional Coaching, conditional Subscriptions, conditional Notifications, Voice control (with a live command reference built from getSupportedPlayerCommands(), grouped by regex match), Offline downloads (list + per-item delete + wipe-all, all reading from FS-sandbox-backed downloads.ts), Support links, Sign out, and Delete account. Notification Preferences app/(root)/notification-preferences.tsx

The master toggle genuinely registers/unregisters an Expo push token (not a cosmetic switch): turning it on prompts OS permission if needed via a modal explainer, then calls registerPushToken; turning it off calls removePushTokens. Every unavailable path (no cloud session, not store-provisioned, OS permission denied) is surfaced as an honest disabled state with explanatory copy rather than a fake-enabled toggle.

  • Loading: full-screen spinner while load() checks provisioning, OS permission, prefs, and token existence
  • Blocked reasons render as a distinct notice card: no cloud connection, not store-provisioned yet, or OS-level denial (with an "Open device Settings" deep link for the last case)

  • First enable flow shows a modal explainer (ShieldCheck icon, what gets sent, "ask permission once") before the OS prompt

Blocked Users app/(root)/blocked-users.tsx

Redeem Invite app/(root)/redeem-invite.tsx

The only trainer-creation path in the app, backed by the dowork-redeem-invite edge function (service role, so invite codes are never client-enumerable). Modeled as an explicit state machine (form | submitting | error | done) rather than loose booleans.   • Already-trainer short-circuit: skips the form entirely, shows a BadgeCheck confirmation and an "Open your Studio" button
  • Anonymous-session block: form stays visible but disabled, with an inline notice and "Add email first" button routing to /account

2Core Training Loop

The core train-log-save workflow starts on the Workouts tab (local SQLite via @mylife/workouts), opens a saved workout into session.tsx which boots directly into a live "playing" state per the fdf942ea fix, ticks a pure reducer every 200ms, records each set's weight and reps to wk_set_weights, and supports hands-free voice control mapped onto the same complete/pause/skip handlers as the manual UI. Completing or ending the workout routes to save-workout.tsx, which annotates the already-persisted session locally and optionally uploads a cloud share if visibility is "Everyone" and Supabase is configured, falling back to a private local save with an inline notice otherwise. Workout construction (Builder and Superset Builder) and exercise discovery (Explore, Exercises, Main Exercises, Exercise Detail) are all backed by the same local SQLite exercise library and workout tables, with cloud involvement limited to the optional trainer-video rail and social share upload; the training loop is otherwise fully functional offline.

Workout Session (playing state) app/(root)/session.tsx

The core screen. Player state is a pure reducer (reducePlayer from @mylife/workouts) ticking every 200ms via setInterval, keyed off status?.state not the whole status object to avoid interval churn. Per the fdf942ea fix, a live session (workoutId param present) boots directly into the "playing" state via createStartedPlayerStatus rather than a separate "ready/start" screen, so the very first render already shows a current set with weight/reps inputs and an active Mark Complete button. Weight/reps drafts prefill from getPreviousPerformance (last logged set for that exercise). Mark Complete writes a wk_set_weights row (recordSetWeight) with a computed estimated 1RM, then advances the reducer; when the reducer reaches "completed" it calls completeWorkoutSession and routes to save-workout. Voice control (useVoiceCoach) maps recognized phrases ("next set", "reps 10", "pause") onto the same handlers as the manual UI. Ending the workout early flushes any in-progress unconfirmed draft set via resolveDraftSetFlush before finalizing, so typed-but-not-confirmed data is not silently dropped. A separate non-live "detail" mode (params.id, no workoutId) renders a read-only past-session summary instead of the live player.

  • Loading: full-screen ActivityIndicator while workout/session load from SQLite
  • Error: GlassPanel error card with "Go Back" if workout/session lookup fails
  • Rest state: same screen swaps the progress ring to a countdown and applies an accent-red highlight in the final 10s; not rendered here (playing state shown per instructions)
  • Voice: toast pill shows last recognized command for 1.2s; mic icon reflects listening/paused/denied/unavailable status

Save Workout app/(root)/save-workout.tsx

Post-session screen. The wk_workout_sessions row is already written by the session engine before this screen loads (params carry sessionId/duration/exerciseCount/totalSets, not the raw session). 3Programs, Plans & Tools

The programs/plans/tools workflow in DoWork is entirely local-first: multi-week programs, plans, 1RM tracking, plate math, progressive-overload rules, and recovery scoring all read and write the on-device SQLite database through `@mylife/workouts`, with zero Supabase/cloud involvement for training-structure data (cloud is reserved for the separate trainer/social/coaching layer documented elsewhere in the app). The "AI Generator" is not a real LLM call; it is a deterministic local algorithm over the seeded exercise library, timed with an artificial delay to feel like generation. There is a notable duplication between `plans.tsx` (an older, simpler plan CRUD screen) and `programs.tsx` plus `program/create.tsx` (a newer, richer week/day builder), which appear to be two competing UIs over similar but not identical data shapes.

4Progress & Analytics

DoWork's tracking and analytics surface is entirely local-first: every screen reads and writes the shared on-device SQLite database through `@mylife/workouts`, with no server calls, so streaks, volume, body metrics, photos, and GPS routes all live and die on the device.
