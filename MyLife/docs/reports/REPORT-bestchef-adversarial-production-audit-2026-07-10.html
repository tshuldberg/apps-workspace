What is actually solid (verified — do not re-litigate)

The adversarial pass confirmed a large amount of real, well-built infrastructure. Give it credit and protect it:

  • RLS is comprehensive. All 60 bc_ tables have RLS enabled; ledger/control tables are correctly definer-only (fail-closed); vote/proof writes routed through SECURITY DEFINER RPCs; moderation RPCs are admin-gated and granted only to service_role.
  • Durable server-side rate limits (bc_consume_action_quota + triggers) enforce votes/comments/follows/reports/likes/appeals with a kill switch — not client-side.
  • JWT split is correct and matches the deploy script; the console holds the service-role key server-only with a fail-closed email allowlist in middleware and every action.
  • Offline layer is strong: contiguous v1..v33 migration chain; 4 of 5 op-queue sweepers mounted; app-death media requeue; cloud-wins reconciliation.
  • Video playback works end-to-end today (durable job → private bucket → console approve → 365-day signed URL → feed). Any claim it's broken is false.
  • Prior breakages genuinely fixed: non-Latin slugify(), real paste-import parser, F-008 comments, F-010 saved submissions, account-deletion worker on a real cron.
  • i18n engine is real: correct CLDR plurals in ar/he/pl, Hermes Intl polyfills for all 21, typed+localized notifications, UGC language tagging, 100% safety-string translation.
  • Gates are wired and green — 328 app tests, 1,423 module tests, typecheck, i18n/raw-strings/rtl/compliance gates all pass and run in CI + the task hook. Nothing is fabricated-green.

Launch-blocking findings — Critical (12)

Deduplicated across dimensions. Status is the adversarial verdict. CONFIRMED = both refuters upheld it; PARTIAL = core real, one detail refined; CRITIC = surfaced by the completeness pass.

CriticalConfirmed

C1.Unmoderated submission images are world-readable at upload

bestchef-submission-images is public=true with an anon SELECT policy over the whole bucket, so every uploaded object is fetchable by URL the instant it lands — before any moderation. The DB moderation_status='pending' gate does not gate the storage object. This is the most dangerous interaction on the platform because it compounds with C3/C4/C5 (no automated screening).

📍 20260429000001_...backfill.sql:10 · 20260428000016_storage_policies.sql:64-67

Fix — make the bucket public=false; serve approved images via short-lived signed URLs only after approval (mirror videos/vote-proofs). Do not enable EXPO_PUBLIC_BESTCHEF_PUBLIC_LAUNCH until this lands.
CriticalConfirmed

C2.Recipe submissions publish unmoderated by default

bc_submissions.moderation_status defaults to 'approved'; the INSERT policy checks only ownership with no with-check, and the guard trigger is UPDATE-only. The app inserts directly and omits the field, so every submission (recipe text, photo, geolocation) is instantly public.

📍 20260424000005_add_bestchef_core_hub.sql:384, :986, :984, :1781

Fix — default to 'pending'; add a with-check forcing pending for non-admins; route publication through the moderation queue.
CriticalPartial

C3.Vote-proof moderation auto-approves via stub classifiers, and is never scheduled

The production moderate_vote_proof entrypoint wires stub providers that always return “safe”/“food”, so the decision plan always approves. Nothing invokes the worker on a schedule. Verifier note (makes it worse): a stub approval both activates the vote and publishes the media — no vote-weight fail-safe.

📍 moderate_vote_proof/index.ts:710, :469-506, :128-129 · 20260610000001_..scheduled_jobs.sql:90-99

Fix — wire real providers in the production entrypoint (never the stub), fail-closed on outage, schedule/queue the worker. Gate launch on a non-stub provider.
CriticalPartial

C4.Submission/comment/post media is enqueued for moderation but nothing screens it

bc_enqueue_media_for_moderation inserts kind='media_asset' rows, but no worker drains them; the console /media page handles only submission videos. Submission/comment/post images are never automatically screened. Refinement: a manual escape hatch exists via the Reports workflow for flagged content.

📍 20260529000004_..media_moderation_enqueue.sql:22-38 · bestchef-console/app/media/actions.ts:59, :108

Fix — build/deploy a worker that drains kind='media_asset' for all owner kinds and both media kinds; extend the console to review image assets. Keep images private until screened.
CriticalPartial

C5.Child-safety reporting duty is unimplemented

No hash-match child-safety provider and no NCMEC/CyberTipline reporting workflow (18 U.S.C. §2258A) exists anywhere in the code — the only occurrence of the requirement is a comment describing an unbuilt worker. Combined with C1 (public bucket) and C4 (no screening), the platform would serve entirely unscreened user photos globally from upload. A hard legal gate for any US wave; should block public GA globally.

📍 requirement appears only as a comment at 20260529000004_...enqueue.sql:9

Fix — contract a hash-match provider (Thorn Safer / PhotoDNA / Cloudflare), run it before any public exposure, wire the mandatory reporting + retention path, register the operator.
CriticalConfirmed

C6.Kitchen grocery-photo AI fabricates results in public builds

kitchen-photo.tsx seeds the candidate field with SAMPLE_GROCERY_PHOTO_JSON and only clears it when a BYO key exists (never in public builds). The review short-circuits on the raw JSON before the broker, so a public user photographing groceries gets hardcoded “Organic Milk”/“Bananas” and can confirm it into real pantry/nutrition data. Ungated.

C10.Monetization is fabricated

No IAP/RevenueCat/StoreKit dependency exists. The tips/subscriptions engines mint fake Stripe IDs (pi_${Date.now()}, sub_${Date.now()}) with no processor. The only creator UI never imports the pay engines, so an approved creator can never be paid. Violates transport-honesty and no-deferral.

📍 cloud/tips.ts:84 · cloud/subscriptions.ts:166 · creator-program.tsx:15-20

Fix — either wire real StoreKit/RevenueCat + Stripe + payout UI, or make the founder decision explicit and remove fabricated success paths. Do not ship fake IDs.
CriticalCritic

C11.Anonymous sybil voting / leaderboard manipulation

Anonymous sign-ins are enabled and no vote/submission/comment path rejects anonymous accounts, opening an unbounded sybil vector: one device can mint anonymous accounts to inflate votes beyond what proof-hash dedup catches.

📍 20260703000002_..integrity_floor.sql · BestChefCloudProvider.tsx:97

Fix — require a verified account or proof-of-humanity before a vote counts toward rankings; weight/quarantine anonymous votes; add device/account-age heuristics.
CriticalPartial

C12.votes_received challenges query a nonexistent column

countMetricForUser selects bc_submissions.vote_count, which does not exist (schema has vote_score). PostgREST returns 400, the error is swallowed, progress freezes at 0. Refinement: only affects bc_challenges rows with metric='votes_received', and the repo seeds none.

📍 cloud/challenges.ts:518-525 · 20260424000005_...core_hub.sql:383

Fix — select vote_score (or sum upvote_count); surface errors; add a regression test.
