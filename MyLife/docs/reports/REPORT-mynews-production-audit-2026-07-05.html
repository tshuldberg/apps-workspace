MyNews Production Audit

2026-07-05 · code security + production readiness · read-only · scope: modules/mynews, apps/mynews, apps/mynews-web, supabase/functions/mynews-*, migrations 20260703000001..3

Verdict

The code that is built (Phases 0-2: scaffold, publish/read, editing desk) is production-grade and green. 505 tests pass (module 302, app 158, web 45), plus typecheck on all surfaces, the web production build, and check:mynews-parity. The trust boundary is carefully designed: articles and suggestions are Ed25519-signed client-side, the server verifies on write and stores signatures so the corpus is re-verifiable, and the private key never leaves the device.

MyNews is not launch-ready as a public app. The blocker is not the built code; it is what is not built. This is a public UGC journalism platform, and the entire moderation and legal safety floor (Phase 3) does not exist. That floor is a hard gate for App Store Guideline 1.2, DMCA safe harbor, and EU DSA. On top of that, the app is not deployed, and there are two real security fixes plus one deploy guardrail to close first.

The honest "launch" is 3 to 5 weeks of focused work away (build the safety floor, fix security, deploy, submit). An invite-only beta is available much sooner for real end-to-end validation, but the two security fixes and deployment are required even for that.

Security findings

High F1 — Direct client INSERT into nw_edit_suggestions bypasses the edge function

supabase/migrations/20260703000003_mynews_editing_desk.sql:170-182 (and 000001:176-179)

The RLS policy nw_edit_suggestions_editor_insert lets any authenticated user INSERT a suggestion row directly through PostgREST with the anon key, as long as editor_id maps to their own auth.uid() and the article is visible. Every legitimate suggestion instead rides the mynews-suggest edge function under the service-role key (store.ts:491; client path confirmed at publish.ts:159), which bypasses RLS. So this insert policy is used by no legitimate client path — it is pure attack surface.

A direct insert bypasses everything the edge function enforces: Ed25519 signature verification (the signature column defaults to ''), the level-based open-suggestion cap, and near-dupe collapse. The DB only enforces the citation-count floor via CHECK, not the signature or the citation scheme.

Impact: unsigned suggestions enter the "re-verifiable corpus"; an attacker can flood any visible article's open-suggestion queue past the cap (harassment); and it is the write path that makes F2 a live stored-XSS vector. nw_articles and nw_journalists already have client-guard triggers for exactly this class — suggestions were missed.

Fix: drop the nw_edit_suggestions_editor_insert policy (all suggestions ride the service-role edge function), or add a trigger blocking direct authenticated/anon inserts, mirroring nw_articles_guard_client_update.

High F2 — Web renders citation URLs as unvalidated href (stored XSS on click)

apps/mynews-web/app/a/[slug]/suggestions/page.tsx:100-102 · shared mapper modules/mynews/src/data/cloud-fetch.ts:460-463

The web suggestions page renders <a href={url} rel="nofollow noopener noreferrer"> with no scheme validation. The shared read mapper toCitations accepts any string, so it provides no defense either. rel does not neutralize the javascript: scheme, and React 19 does not sanitize href.

The edge function validates https:// at insert and HttpsUrlSchema exists in models.ts:14, but neither applies on the read/render path. Chained with F1 (which lets a javascript:… citation into the DB unvalidated), any visitor who clicks the crafted citation on a public article executes attacker JavaScript on the mynews.app origin. The Expo app defends here (suggestion/[id].tsx:329 gates on startsWith('https://')); the web does not.

Fix: validate citation URLs to http/https in toCitations (fixes both surfaces) and defensively at the web render.

Medium F3 — verify_jwt deploy trap on mynews-review

supabase/functions/_shared/mynews-http.ts:41-52 · supabase/config.toml:418-432

mynews-review's author gate authorizes off parseJwtSub, which decodes the JWT without verifying its signature and relies on Supabase's verify_jwt = true. config.toml correctly omits the mynews functions (default on) and warns against listing user-facing functions with verify_jwt = false, so the default deploy is safe.

The risk is operational: the founder-ops docs say only "deploy the 3 functions." If someone copies the BestChef --no-verify-jwt pattern, an attacker can forge a sub and accept/reject suggestions as any author.

Fix: pin an explicit deploy note (never --no-verify-jwt for review) and a post-deploy check that an unauthenticated review call returns 401.

What is clean verified

  • Secrets: no tracked .env, no hardcoded keys, no service-role key in client/web source. Only anon key + EXPO_PUBLIC_MYNEWS_* / MYNEWS_SUPABASE_*.
  • RLS hardening: the migration's adversarial-review appendix closed real leaks (draft thread visibility, client publish/insert bypass, a membership oracle). Money/job/verification tables carry RLS with zero client policies; public-URL columns are CHECK-forced to https.
  • Markdown rendering: no markdown-to-HTML pipeline; body_md renders as escaped React text on both surfaces. No dangerouslySetInnerHTML in app/web source.
  • Honesty boundary: unconfigured/unreachable/signed-out/no-profile render honest states; no fabricated counts, no demo adapter in the runtime path, publish/share never fake success.
  • Auth + key custody (Expo): session token in SecureStore, never logged or sent cross-origin; Ed25519 private key in SecureStore; only signature + pubkey leave the device.
  • Build guard: check-build-env.mjs fails production builds with no RevenueCat key and blocks test-mode entitlements.

Production-readiness gaps (not code bugs)

Blocker R1 — No UGC moderation or legal floor

The true launch blocker. Anyone can publish articles and suggestions that become public on the web, but:

  • nw_reports is a table with an insert policy but no client code writes to it — users cannot report content.
  • No block, mute, or hide UI anywhere in the app.
  • No moderation console (BestChef has one; MyNews has nothing equivalent).
  • No DMCA designated agent / repeat-infringer policy; no NCII / TAKE IT DOWN 48h pipeline; no DSA Art 16/17 notice-and-action or EU contact.
  • No in-app Terms / Privacy / Community Guidelines (nw_terms_acceptance exists but is unused).

Apple Guideline 1.2 requires UGC apps to have a content filter, a report mechanism, a block-users mechanism, and published contact info. Launch-blocking for a public submission and for DMCA safe harbor. This is Phase 3 and is unbuilt.

Ops R2 — Not deployed

No Supabase project, empty DEFAULT env, functions undeployed. Go-live: create project; db push all three migrations; deploy the three functions (verify_jwt on for review); enable anonymous sign-in + allowlist mynews://auth-callback; set app + web env; live end-to-end (register, publish, suggest, review, read on web, RSS); device QA the magic-link deep link. Longer track: Stripe Connect, EAS/ASC, RevenueCat products, a real domain (fallback origin https://mynews.app at origin.ts:7 is a placeholder). Free-tier Supabase pauses after 7 idle days.

Final production-readiness plan

Sequenced so security and the safety floor land before any public exposure.

Track 0 — Security fixes · ~1 day · before any deploy

  • F1: drop nw_edit_suggestions_editor_insert (or add a client-guard trigger) in a new migration + an RLS test proving direct inserts are rejected.
  • F2: validate citation scheme in toCitations + defensively at the web render; add a javascript: citation test.
  • F3: add the verify_jwt-on deploy note + post-deploy 401 check to the runbook.
  • Run gate:function:changed, the mynews baseline block, check:mynews-parity. Land to main.

Track 1 — UGC safety + legal floor · ~2 to 3 weeks · the real public gate

Author a plan (next queue number; 37 is Meerkat's): report flow wired to nw_reports on app + web; block/mute UI + enforcement; a moderation console (or minimal reviewer surface over nw_reports); DMCA agent + repeat-infringer policy + takedown; NCII/TAKE IT DOWN 48h pipeline; DSA Art 16/17 + EU contact; in-app Terms / Privacy / Community Guidelines + acceptance.

Track 2 — Deploy + go-live · founder-ops · ~2 to 4 days · parallel with Track 1

The R2 checklist. Keep the free-tier Supabase warm or upgrade before launch.

Track 3 — Submit

Full public path: complete Tracks 0-2, device QA, App Store 1.2 self-check, submit. Interim option: an invite-only TestFlight beta with a known-user allowlist can start after Tracks 0 + 2 (no public UGC exposure defers the 1.2 floor), giving real end-to-end validation while Track 1 builds toward public GA.

Audit method: manual read of the trust-boundary code (edge functions, RLS migrations, RPCs, triggers), a parallel read-only review of the client/web surfaces, and the green baseline gate. Not a substitute for a professional penetration test before a public launch handling PII and payments.
