Storage lifecycle and cross-device recovery

Scheduling, retention, mirrors, repair, destination moves, credential rotation, deletion, and fresh-install locator discovery are implemented across the shared core, mobile, and web.

Typechecks passParity passesMobile 1,268/1,268Sandbox listener failures unchanged

Outcome

Backups publish bounded, provider-discoverable locator records on every primary and mirror destination. A fresh install can list and open those backups with destination credentials and the recovery key. Every lifecycle action is driven by persisted storage truth and reports partial work without inventing completion.

The existing hosted GET /api/storage/v1/backups route was sufficient. packages/meerkat-relay was not changed.

Implemented capabilities

Retention

  • Keep-last is bounded to 1 through 100 and max age to 1 through 3,650 days.
  • Deletion requires a backup to fall outside both windows.
  • The last verified complete backup is preserved.
  • A mirror is protected whenever its primary is not verified.
  • Backup ownership is classified from real prefixed object rows by data class, so policies sharing a destination cannot delete each other's data.

Scheduling

  • Pure decisions cover due, not due, disabled, invalid, unavailable, revoked, quota full, active, and paused states.
  • Last-run evidence is keyed by data class and destination and comes only from complete backups with verified objects.
  • Mobile uses the existing opt-in background-sync and gated OS registration discipline. Manual execution remains available.
  • Web runs best effort only while open and visible and says so directly.

Repair and moves

  • Repair prefers verified local bytes, then a mirror, and verifies source, upload, and read-back before changing state.
  • Backup rows return to complete only after every tracked object and the manifest verify.
  • Move remains copy, read-back verify, then source delete, with exact live progress on mobile and web.

Credential rotation and deletion

  • WebDAV and S3 secrets are securely replaced, probed, health-checked, and rolled back on failure before paused jobs resume.
  • Broker reconnect atomically swaps the verified vault reference.
  • Account deletion revokes every destination, optionally deletes remote encrypted objects, deletes broker vaults and the hosted account, clears secrets, and clears all mk_storage_* rows only after remote work succeeds.
  • Reports use exact counts and the completed flow is idempotent.

Cross-device discovery

  • Every backup uses mkb1.<sha256(backupId)>. as a provider-safe flat prefix.
  • locator.json, manifest-ref.json, the encrypted manifest, and encrypted objects are written on every destination.
  • Discovery bounds pages and objects, validates locator and path agreement, validates the manifest reference, and requires manifest hash evidence.
  • Mobile and web fresh-install restore share the same byte-twin discovery consumer.

Judgment calls

  1. A flat provider-safe prefix keeps the discovery convention identical across local, WebDAV, S3, broker, and hosted adapters.
  2. Discovery proves locator and manifest hash evidence. Full cryptographic authenticity still occurs when the recovery key opens the manifest.
  3. A mirror failure never downgrades a verified primary. It is reported as partial mirror coverage.
  4. Account cleanup retains local evidence until requested remote operations succeed, enabling honest retry.
  5. Legacy backups without the v1 prefix are not retention-deleted and do not count as schedule evidence.
  6. Web scheduling is foreground best effort. Mobile OS work remains behind the existing capability gate.
