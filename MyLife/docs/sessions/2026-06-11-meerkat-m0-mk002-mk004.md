## MK-002: inbound policy enforcement (closes audit C12)

A paired peer is authenticated, not authorized. `applyReceivedDocumentChanges`
(packages/sync/src/protocol/sync-session.ts) is the single inbound chokepoint and
now enforces, fail-closed, before any row is written:

- **revocation** - `isDeviceRevoked(peer)` rejects everything from a revoked device.
- **authorization** - workspace session: active member of the (non-archived)
  workspace; personal session: a paired device. Else rejected.
- **module ownership** - the change's table prefix must resolve to the enabled
  module the batch claims (blocks foreign-module smuggling).
- **scope caps** - session scope (personal_replica / shared_workspace) must be
  within the module/entity cap; no declared policy => device_local => rejected;
  non-shareable modules capped at personal_replica.
- **tombstone no-resurrection** - cannot re-insert a deleted row with a non-newer
  write; an applied DELETE records a tombstone.

Rejections are written to a new `sync_inbound_audit` table (one row per rejected
change; one row for a revoked/unauthorized peer) and never applied.

New: `packages/sync/src/protocol/inbound-policy.ts` (pure `evaluateInboundChange`,
exported RN-safe), `sync_inbound_audit` table + `insertInboundAudit` /
`getInboundAudit` / `getTombstone` / `deleteTombstone` query helpers,
`SyncInboundAudit` type. Engine passes `modulePolicies` into both session sites.

Tests: 18 pure red-team matrix (inbound-policy.test.ts) + 8 DB-backed apply
(inbound-policy-apply.test.ts). A background security review applied two fixes:
identifier guard inside `hasNewerLocalVersion`, and blocking archived workspaces
in `resolveInboundAuth`.

### Fixes found while verifying the desktop path

Three real defects surfaced and were fixed (all caught by adding the store-and-forward
test + running the CLI under tsx):

1. **ESM/CJS interop** -- five sync files imported named exports from the CJS
   `tweetnacl-util` (`import { encodeBase64 } from 'tweetnacl-util'`), which Node's
   ESM loader cannot destructure, so `@mylife/sync` failed to load in a plain Node
   (desktop CLI) process even though Vitest bundled it fine. Switched to
   default-import + destructure (matching the existing `import nacl from 'tweetnacl'`).
2. **Mailbox-drain race** -- the relay drains its TTL mailbox to a peer
   immediately on join (before `ready`), but `WebSocketRelaySession` dropped any
   envelope that arrived before the app called `onMessage`, silently losing the
   entire store-and-forward path. Now buffers pre-handler envelopes and flushes
   on the first `onMessage`; `MeerkatDirectClient` does the same for pre-`onReceive`
   shares. New `direct-client-e2e` mailbox test covers it.
3. **Token format** -- the relay requires a token >= 16 chars; the CLI now hashes
   any user phrase (sha512Hex, 64 hex) into the rendezvous token, so a friendly
   shared phrase works and the relay only sees the hash.

Verification reality: the library + relay are proven cross-client by
`direct-client-e2e.test.ts` (real ws server, two clients, live + mailbox) and by
in-process diagnostics against an external relay process. The two-terminal CLI
round-trip could not be fully exercised inside this sandbox (backgrounded tsx
processes are not scheduled enough CPU to flush their socket writes, and orphaned
demo processes could not be killed), but the CLI loads correctly under tsx and is
a thin wrapper over the tested client. It should run normally on real, separate
macOS/Windows machines.

### M1 started: MK-009 + MK-012 (same session)

- **MK-009 receipts + per-peer outbox.** Previously the initiator blanket-marked
  every unsynced change as synced after ANY session: with two paired peers, a
  change delivered to B would silently never deliver to C via the change log.
  Now SYNC_DATA carries the covered change-log ids; the responder writes
  sync_receipts and replies SYNC_ACK; the initiator records receipts on ack and
  marks a change synced only when EVERY active paired device has a receipt
  (evaluated over all unsynced changes, so partial acks self-heal across
  sessions; an un-acked batch stays pending -- no silent drops). New
  `getReceiptPeersForChange` query; receipts INSERT OR IGNORE; initiator
  sessions now have stable ids. `receipts-outbox.test.ts` runs the exact AC:
  A paired with B + C; after A->B the change is delivered to B but still
  pending; after A->C both receipts exist and only then is it marked synced.
- **MK-012 replay protection.** `protocol/replay-guard.ts`: per-session sliding
  window of frame hashes (default 512) + wire-timestamp skew budget (default
  5 min), wired into the responder receive loop before any processing;
  rejections audited to sync_inbound_audit as `replayed_frame` /
  `timestamp_skew`. `replay-guard.test.ts`: unit matrix (dup rejected, skew
  past/future/NaN rejected, window eviction) + live-session AC: a wired pair
  re-injects every SYNC_DATA frame verbatim; the duplicate is rejected +
  audited and the note applies exactly once.

### M1 completed: MK-010 + MK-011 + MK-013 + MK-014 (same session)

The crypto-negotiation cluster, landed in dependency order:

- **MK-010 KDF v2.** `deriveKeyV2` = RFC 5869 HKDF (extract-then-expand over
  HMAC-SHA-512, the node layer's cross-checked impl; the plan said SHA-256 but
  nacl ships no SHA-256 primitive -- the RFC construction is the point).
  Sessions advertise `kdfVersions` in the encrypted SYNC_OFFER/ACCEPT, pick the
  highest mutual, and default to v1 for peers that predate negotiation.
  kdf-negotiation.test.ts adds the suite's first fully ENCRYPTED end-to-end
  sessions: v2<->v2 negotiates 2; v2 vs a forced-v1 peer falls back and still
  syncs. (`supportedKdfVersions` option makes the cross-version test honest.)
- **MK-011 Noise forward secrecy.** The dormant NoiseHandshake is load-bearing:
  the initiator's ephemeral hello + the responder's reply ride INSIDE the
  encrypted negotiation, and the data channel switches from the static-derived
  key to the per-session key (`negotiation.forwardSecrecy = true`); pre-Noise
  peers keep the static channel (`supportsForwardSecrecy` fallback window).
  noise-session.test.ts proves: per-session keys differ and ciphertext under
  session N's key cannot open under N+1's; a captured SYNC_DATA frame from a
  Noise session is UNREADABLE with the static key (the channel really moved);
  the fallback path still syncs, with a control proving the harness sound.
- **MK-013 signed batches.** `protocol/batch-signature.ts` signs every
  SYNC_DATA over (module, snapshot digest, covered change ids) with the
  sender's Ed25519 key; the responder verifies against the
  handshake-authenticated device id BEFORE applying. Invalid -> rejected +
  audited (`bad_batch_signature`); valid -> an `accepted` /
  `batch_author_verified` audit row surfaces the author for the activity
  trail. Load-bearing even on an unencrypted channel -- proven by a live
  session on a plaintext channel where a digit is flipped inside the
  SYNC_DATA JSON on the wire: rejected, nothing applied, and the sender holds
  no receipt for the un-acked batch (MK-009 composing with MK-013).
- **MK-014 relay-first defaults.** The dial ladder and the bootstrap
  preference seeding both move to `[5, 1, 4, 2, 3]` (Relay > LAN > Direct >
  Nearby; BLE stays wake-up-only). Ranked choices still lead; the ladder
  backfills. One transport.test.ts expectation updated deliberately per
  D1/D2. The hub-UI label/availability sweep is the remaining sliver, folded
  into the next hub UI pass (the meerkat app's labels are already truthful).
