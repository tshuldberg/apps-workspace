Step 1: Same-Account Device Linking Evidence

Goal: prove that a user can export an identity backup on one real device and restore the same identity on another real device, and prove bad recovery material fails closed.

Setup

  1. Prepare two physical devices, named Device A and Device B in the evidence notes.
  2. Install the same Meerkat build on both devices.
  3. Start both devices from fresh installs or reset app data.

Run

  1. On Device A, complete onboarding with a recognizable display name.
  2. Record the identity safety code or fingerprint shown during onboarding or in identity/settings.
  3. Open Settings and find the recovery or identity backup section.
  4. Copy both the recovery key and encrypted identity backup.
  5. Screenshot the recovery section with secrets redacted.
  6. On Device B, choose Already have a backup? Restore your identity.
  7. Paste the recovery key and encrypted backup from Device A.
  8. Submit restore and confirm Device B enters the app as the same identity.
  9. Compare Device B's safety code or fingerprint to Device A.
  10. On Device B, create one community or send one message so the restored identity is visibly active.
  11. Reset Device B again.
  12. Try restore with an intentionally wrong recovery key or corrupted backup text.
  13. Confirm the app shows an error and does not silently create or claim the Device A identity.

Pass Criteria

  • Device B shows the same safety code or fingerprint as Device A after valid restore.
  • Device B can continue using the restored identity.
  • A wrong key or corrupted backup fails with an honest error.
  • No UI claims cloud backup or hosted recovery unless that service is actually connected.

Evidence To Save

  • Device A and Device B model and OS version.
  • Build identifier.
  • Redacted screenshot of Device A recovery export.
  • Screenshot of Device B after successful restore with matching identity proof.
  • Screenshot of failed bad-material restore.
  • Short note describing the exact values compared, with secrets redacted.

Step 2: Production Relay Launch Evidence

Goal: run the web launch E2E against a real WebSocket relay so the relay-dependent test executes instead of skipping.

Setup

  1. Obtain the production or staging relay WebSocket URL, for example wss://relay.example.com.
  2. Confirm it is a real ws:// or wss:// URL reachable from this machine.
  3. Keep the shell clean of stale relay env values.

Run

pnpm --filter @mylife/meerkat-web test:e2e

Confirm the baseline has 3 passed tests and 1 honestly skipped relay test.

MEERKAT_E2E_RELAY_URL=wss://YOUR-RELAY-HERE pnpm --filter @mylife/meerkat-web test:e2e
  1. Confirm the relay-dependent test is not skipped.
  2. Save the full command output.
  3. If the relay run fails, copy the failing test name, error text, relay URL used, and timestamp into errors_log.md, then fix the real defect before retrying.

Pass Criteria

  • All 4 Playwright tests pass when MEERKAT_E2E_RELAY_URL is set.
  • The relay guard performs a real WebSocket handshake.
  • No test is softened to pass against an absent or fake relay.

Evidence To Save

  • Relay URL used.
  • Timestamp of run.
  • Full terminal output.
  • Screenshot or trace if a browser failure occurs.

Step 3: Downloads Real Artifact QA

Goal: prove global Downloads works with real community files and local bytes, including present bytes, absent bytes, report/hide, request-again, and removed-file non-saveable states.

Setup

  1. Use at least one physical mobile device for mobile QA.
  2. Use a desktop browser for web QA.
  3. Use a real community and channel.
  4. Use real files: one small image, one small PDF or text file, and one unsafe inline MIME type if available.
  5. Do not create file rows by editing SQLite or IndexedDB directly.

Mobile Run

  1. Open Meerkat mobile.
  2. Create or open a community with at least one channel.
  3. Attach or share a real file through the normal app UI.
  4. Open the community Files screen.
  5. Tap the global Downloads entry point.
  6. Confirm the Downloads screen opens.
  7. Search for the file by name.
  8. Filter On device.
  9. Open the file.
  10. Save the file.
  11. Enter select mode, select multiple present files, and run bulk save.
  12. Report one file.
  13. Confirm the reported file no longer appears in the normal Downloads list for that device.
  14. Create an absent-byte state through normal UI behavior only, for example a second device that has the signed file message but not the blob bytes, or a visible remove-local-copy action if one exists.
  15. Filter Removed.
  16. Confirm the removed file cannot be selected or saved.
  17. Tap request again.
  18. Confirm the app either requests the file through a real available path or shows an honest reason it cannot request it.

Web Run

pnpm --filter @mylife/meerkat-web dev
  1. Open the local URL shown by Vite.
  2. Complete onboarding or restore a test identity.
  3. Join or create the same test community.
  4. Open Files.
  5. Click All downloads.
  6. Confirm the Downloads screen opens.
  7. Search for the file by name.
  8. Filter On device.
  9. Use View for a safe inline file.
  10. Use Save for one file.
  11. Select multiple present files and run bulk download.
  12. Report one file and confirm it is hidden locally.
  13. Confirm unsafe or unknown MIME types download instead of opening inline.
  14. Confirm absent-byte rows show request-again or honest unavailable copy.

Pass Criteria

  • Settings and community Files both reach global Downloads.
  • Search and status filters work.
  • Present files can open and save.
  • Bulk save or download works for present files.
  • Reported files hide locally.
  • Removed or absent-byte files cannot be selected or saved.
  • Request-again never claims success unless bytes are actually restored.
  • Web unsafe MIME types do not open inline.
