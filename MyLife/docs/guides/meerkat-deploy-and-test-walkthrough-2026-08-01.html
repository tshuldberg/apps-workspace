0 · The mental model (read once — it prevents every confusion later)

You asked to connect your devices to "your account." Meerkat deliberately has no accounts. Five facts, and everything downstream follows:

  • Every device is its own identity. Your iPhone, your MacBook browser, and your PC browser each generate their own keypair on first launch. There is no username, no password, nothing to log into.
  • "You" = your devices, linked. You pair your devices to each other, then link them into a person group. After that, member lists show one row: "Trey · 3 devices". Your friend does the same.
  • The unlock is per store rail. $4.99 once, bought through Apple on iOS (free for you both in TestFlight's sandbox). The web has a separate rail; for this private test the web testbed grants it honestly.
  • The relay is a blind mailbox. One small server that forwards and briefly holds sealed envelopes. It has no database, no keys, no user list, and reads exactly two settings. Every device of yours and your friend's points at the same one.
  • Communities are joined per device. Membership does not auto-copy to your other devices: each device joins with the invite link, then person-linking collapses them into one member row. This surprises everyone exactly once.

2 · Deploy the relay

DO THIS NOWYOU~15 min~$7/moOne time

One small container. It needs no database, no secrets, no API keys — it reads only a port, a host, and a message-retention setting. Browsers refuse plain ws:// from an https:// page, so you need a host that provides HTTPS automatically. Render does, with a one-click blueprint already committed to your repo.

Recommended

A · Render

One-click blueprint at the repo root. Auto-TLS, health-checked, 24-hour message retention already preset. ~$7/mo starter plan — the free tier sleeps and stalls the first sync.

Alternative

B · Fly.io

Same container, CLI-driven. deploy/fly.toml is ready and now carries the 24-hour setting too.

If you own a VPS

C · Docker + Caddy

deploy/docker-compose.yml has a Caddy TLS edge commented out. Uncomment, set your domain, point DNS, bring it up.

Path A · Render, click by click

  1. YOUOpen the one-click deploy link

    Go to render.com/deploy?repo=https://github.com/tshuldberg/MyLife — this is the button from your own repo's relay guide. Sign in with GitHub if prompted and authorize Render to read the MyLife repository.

    Render reads render.yaml from the repository root and pre-fills the whole service for you: Docker runtime, the relay Dockerfile, the health check, and the environment values.

    You should see: a "Blueprint" / "New Blueprint Instance" screen listing one web service named meerkat-relay.

  2. YOUName it and pick the paid starter plan

    Give the blueprint instance any name (for example meerkat). Confirm the service plan reads Starter (about $7/month), not Free.

    Why not free: Render's free tier sleeps after inactivity. A sleeping relay stalls your friend's first sync and drops parked messages when it restarts.

  3. YOUClick Apply / Create and wait for the build

    Render pulls the repo, builds the Docker image, and starts the service. The first build takes a few minutes. Watch the Logs tab until you see the relay start and the health check go green.

    You should see: the service status turn Live in the Render dashboard.

  4. YOUConfirm the retention setting actually landed

    Open the service → Environment tab. You should see two variables, both set by the blueprint:

    • HOST = 0.0.0.0
    • RELAY_MAILBOX_TTL_MS = 86400000

    If RELAY_MAILBOX_TTL_MS is missing, add it manually with that exact value and redeploy.

    This is the single most important setting on the page. The relay's built-in default is 5 minutes. A message you send while your friend's app is closed would evaporate before they ever open it. 86400000 ms is 24 hours, the maximum the relay allows.

  5. YOUTest it in a browser

    Copy your service URL from the top of the Render page. It looks like https://meerkat-relay-xxxx.onrender.com. Open that URL with /healthz on the end:

    https://YOUR-SERVICE.onrender.com/healthz
    You should see exactly: {"ok":true,"connections":0} — nothing else. That two-field answer is deliberate: the relay knows nothing else to tell you.

  6. YOUWrite down your relay address

    Take the same URL, swap https for wss, and drop any trailing slash. That is the address every device uses and the value Claude bakes into the build:

    wss://YOUR-SERVICE.onrender.com

    No path, no port, nothing after the hostname.

Path B · Fly.io instead (CLI) 
cd /Users/trey/Desktop/Apps/MyLife/packages/meerkat-relay

Run these from the relay package root, not the deploy folder — that directory is the Docker build context the Dockerfile expects. The 24-hour retention is already in fly.toml. Your address is wss://your-app.fly.dev.

Why not the full 15-service production stack?

That topology (Caddy, Postgres, ClamAV, LiveKit, NCMEC filer, and eleven subdomains) is for a public launch. For two friends, every one of those is optional — verified service by service. The account service only gates public publishing; LiveKit only powers the channel "Room" button (1:1 calls are peer-to-peer); the push gateway only wakes closed apps. The small relay alone carries communities, DMs, pairing, and file sync.

3 · App Store Connect + RevenueCat

DO THIS NOWYOU~1 hourOne time

This is account paperwork, not engineering — but it is unavoidable. The app checks with RevenueCat on every launch to confirm the $4.99 unlock, and if it cannot reach a configured purchase system it locks itself. There is no developer bypass anywhere in the code; that was a deliberate honesty decision. In TestFlight, purchases run in Apple's sandbox, so neither you nor your friend is charged anything.

Part 1 · Apple Developer portal (identifiers)

  1. YOUCheck the main App ID has Push enabled

    Go to developer.apple.com → Account → Certificates, Identifiers & Profiles → Identifiers. Find com.mylife.meerkat (EAS created it during your interactive build).

    Click it and confirm these capabilities are checked: Push Notifications, App Groups. Save if you change anything.

  2. YOUCreate the App Group

    Identifiers → the + button → App Groups → Continue. Description: Meerkat. Identifier: group.com.mylife.meerkat exactly. Register.

    Then go back into the com.mylife.meerkat App ID, edit the App Groups capability, and tick the group you just made.

    Why: the iOS share sheet ("Save to Meerkat") is a second mini-app inside your app, and the two halves talk through this shared group.

Part 2 · App Store Connect (the app record and the $4.99 product)

  1. YOUConfirm the Paid Apps agreement is active

    At appstoreconnect.apple.com → Business (or Agreements, Tax, and Banking). The Paid Applications agreement must show Active, with banking and tax details filled in.

    Do this first. Until this agreement is active, in-app purchases do not work even in the sandbox, and the symptom is a purchase sheet that silently fails. It is the most common cause of "the unlock button does nothing."

  2. YOUCreate the app record

    Apps → the + → New App. Fill in:

    • Platforms: iOS
    • Name: Meerkat (if taken, any unique name works for testing)
    • Primary language: English (U.S.)
    • Bundle ID: com.mylife.meerkat from the dropdown
    • SKU: meerkat-ios (internal only, any string)
    • User Access: Full Access

    Create it. Then open App Information and note the Apple ID — a long number. Send that to Claude for the submit configuration.

    You should see: the app in your Apps list, state "Prepare for Submission".

  3. YOUCreate the one in-app purchase

    Inside the app record → Monetization → In-App Purchases → +. Then:

    • Type: Non-Consumable (a one-time permanent unlock)
    • Reference Name: Meerkat App Unlock
    • Product ID: meerkat_app_unlock — must match exactly, character for character
    • Price: $4.99 (US tier)
    • Localization: add English (U.S.), Display Name Unlock Meerkat, Description e.g. "One-time unlock for full private use."
    • Review screenshot: any 640×920+ image is fine for now

    Save.

    The product ID is hardcoded and price-locked in the app. If you type anything other than meerkat_app_unlock, the app will not find the product and the unlock stays unavailable.

Part 3 · RevenueCat (produces the key Claude needs)

  1. YOUCreate the project and app

    At app.revenuecat.com, sign up or sign in. Create a new project called Meerkat. Inside it: Apps → + New → App Store. Set the bundle ID to com.mylife.meerkat.

  2. YOUConnect it to App Store Connect — two different keys

    App Store Connect issues two kinds of .p8 key and RevenueCat asks for both, in different fields. Uploading the wrong one gives the error "Invalid file name, it should be SubscriptionKey_XXXXXXXXXX.p8".

    Both live under Users and Access → Integrations, in the left sidebar:

    • App Store Connect API → generates AuthKey_XXXX.p8. Grant App Manager access. Used for reading app and product metadata — and by eas submit. Keep this one.
    • In-App Purchase → generates SubscriptionKey_XXXX.p8. Used to validate purchases server-side. This is the one the purchase-key upload field wants.

    Each key downloads exactly once, so save both before uploading. Note the Key ID beside each, and the Issuer ID for the API key.

    These are private keys. Keep them out of the repository and out of chat. Nothing in this project ever needs their contents — only the public appl_ key from the next step gets shipped.

  3. YOURegister the product

    In RevenueCat → Product catalog → Products → + New. Product identifier: meerkat_app_unlock, attached to your App Store app.

    Optional but tidy: create an Entitlement and attach the product to it. The app reads the customer's entitlements to decide "unlocked".

  4. YOUCopy the public API key

    Project settings → API keys → the Public app-specific API key for your Apple app. It begins with appl_.

    Send that string to Claude along with your wss:// relay address.

    Only the public appl_ key. Never the secret key that starts with sk_ — the public key is the one designed to ship inside an app binary.

8 · Link your own devices into one "you"

Each person separately~10 min

Two stages in order: pair (the devices establish cryptographic trust) then link (you declare the paired device is also yours, forming your person group). The link button stays disabled until you confirm safety codes — that is enforced in code, not a suggestion.

iPhone to iPhone, sitting together

On both phones: Sync → Pair in person → hold the phones near each other → both show the same five emoji → compare them out loud → both confirm. No server involved at all. (This is also the feature your test will prove on real hardware for the first time.)

iPhone to MacBook or PC (the copy-paste path)

  1. Get the computer's pairing code

    In the web app: Sync → Pairing section → copy the code beginning with MKPAIR1-.

    Why copy-paste here: browsers have no radio access, so the in-person ceremony is impossible on the web by design. The app says so rather than offering a button that cannot work.

  2. Paste it into the phone, and send the phone's code back

    On the phone: Sync → paste the computer's code → Pair device. Then copy the phone's own MKPAIR1- code and paste it into the computer → Pair device there too. Both sides must do it.

    You should see: "Paired devices: 1" (or higher) on both.

  3. Compare safety codes and mark them verified

    Look at the safety code on each device and confirm they match what each shows for the other. Mark verified.

    Until you do this the link button is greyed out, with the message "Check this device safety code before linking it as your own device."

  4. Link it as your own device

    On either device: Messages (or Settings) → Own devices panel → Link this second device → confirm on the other device when prompted.

    Repeat the whole sequence for each additional device (your PC, a second phone).

    You should see: in a community member list, one row for you with a device count rather than separate rows per device.
What actually travels between your own devices today
Your person identity, display name, channel read positions, and library progress replicate. These do not: settings, the unlock (each device restores its own), community membership (each device joins with the invite link — step 10), and incoming direct messages. Your outgoing DMs reach your own devices, but a friend's messages only arrive on devices that friend has paired with. Practical advice: do your direct messaging on the phone, and treat computers as community and file surfaces. This is listed in the limitations section too.

Troubleshooting

The web page is stuck on "Booting Meerkat…"

You opened it over plain http://. Browsers withhold the cryptography the app needs outside a secure context, and this failure has no error screen yet. Use the https:// tunnel link or localhost.

"No connection server configured" even though I set one

A stale health check. Open /healthz in a browser to confirm the relay answers, then re-save the address in the app.

The purchase sheet never appears
