1. Verified seam ground truth, and three corrections to the companion report

Six verification agents ran against source (descriptor/scopes, theme/parity, media/library, torrent, rooms/live, feed/monetization/identity); the author re-read the load-bearing lines directly. The five seams hold. Three findings change the design.

Correction 1: new descriptor FIELDS break old verifiers; new TABLES and new kind VALUES degrade gracefully. Conditional canonical append (protocol/community.ts:180-238) keeps new code verifying old descriptors. It does not do the reverse: an old client canonicalizes only the fields it knows, produces different bytes than the owner signed, and rejects the revision as forged. A new channel kind VALUE rides an existing slot (old clients verify fine and render the designed 'unknown' read-only banner, community.ts:526), and a new owner-signed EVENT TABLE simply fails closed to invisibility on old clients (defaultScope: 'device_local'). Therefore: the layout document, capability manifest, and tier definitions ride ONE new signed event table (cm_layout), not descriptor fields. The descriptor gains nothing in Phase 1.

Correction 2: exactly one trailing conditional descriptor slot exists. canonicalDescriptor ends with ...(organization ? [organization] : []). A second trailing conditional slot is positionally ambiguous. When a verifier-visible descriptor field is eventually needed, the only signature-safe mechanism is NESTED conditional append inside the organization slot: [categories, layout] today, [categories, layout, <newField>] when set; inner length disambiguates; existing bytes unchanged. No implementer may add a second trailing slot.

Correction 3: the parity gate does not self-extend. check-meerkat-parity.mjs is imperative; the chatKitTwins tuple list is the extension model, and nothing fails when a *-core.ts has no lock. Already unlocked today: feed-view-core.ts, join-flow.ts (~106 lines of real drift), public-directory-client.ts, discover-core.ts, public-reader-core.ts, public-join-client.ts. Phase 0 fixes this before the platform multiplies core files.

2. Platform architecture: the composition spine

Four artifacts. Everything else in this plan is a block plugged into them.

2.1 Block registry BUILD

The generalization of MEDIA_TYPE_REGISTRY, delivered as a pure core: data/block-registry-core.ts + byte twin src/lib/block-registry-core.ts.

interface BlockContract {
  configSchema: ZodType;              // per-block config carried in the layout document
  dataSources: readonly string[];     // exact cm_/mk_ tables + blob classes this block may read
  requires: readonly CapabilityKey[]; // capability-manifest gates
  surfaces: 'home' | 'channel' | 'both';
  channelKind?: CommunityChannelKind; // when the block is the view contract for a kind
  fallback: 'placeholder';            // unknown/ungated blocks render a safe honest card
}

Block types v1: hero, chat, posts, timeline, gallery, video_gallery, video_player, live_stage, shortform_pager, files, store, tiers, embed, events, page, members. Renderers stay OUT of the core (they touch native modules): per-surface renderer maps at components/blocks/registry.tsx and ui/blocks/registry.tsx, keyed by block type, mirroring how the theme seam separates pure resolution from rendering. An unregistered or capability-ungated type renders BlockPlaceholder with honest copy.

Sandbox rule, enforced by test: a renderer receives a BlockDataContext exposing only query functions for its contract's tables; a lint-style test (block-data-scope.test.ts, both surfaces, in the chat-kit-no-providers style) greps each renderer for out-of-contract db access. Blocks never fetch the network; the embed consent gate is the single sanctioned exception.

2.2 The community composition document: cm_layout BUILD

One new owner-signed event table carries layout, capability manifest, and tier definitions together, modeled line-for-line on cm_community_identity:

  • Table cm_layout: id (signature-bound event id), community_id, revision, layout_blob (capped 32 KB), tombstone, updated_at, signed_by, signature. Entity rule shared_workspace/shared_workspace, lww; the existing rule-less-table guard tests cover it automatically; the id = rowId invariant applies.
  • Protocol packages/sync/src/protocol/community-layout.ts: canonical domain meerkat-community-layout-v1; createCommunityLayoutEvent, verifyCommunityLayoutEvent (owner-only, fail-closed), resolveCommunityLayout (re-verify all, highest verified revision, null on tombstone). Register validateCommunityLayoutRow in SIGNED_ROW_VALIDATORS; DELETE rejected (tombstone events only).
  • Blob format: new package packages/meerkat-layout/ mirroring meerkat-theme (codec meerkat-layout:v1:, Zod schema, cap, typed decode errors). Content: { capabilities, tiers, home: BlockNode[], channels: Record<channelId, BlockNode[]> }. Sync carries it opaquely as a capped string, exactly like the theme blob.
  • Choke point: data/community-layout-core.ts (+ twin) exports resolveActiveLayout mirroring resolveActiveTheme: verified blob decoded and validated, else fail SAFE to legacy rendering. Malformed or unknown block nodes degrade per-node to placeholder, never whole-screen.
  • Degradation: old clients never see the table and render legacy surfaces; new clients in legacy communities resolve null and render legacy. Zero signature risk in both directions.

2.3 Capability manifest semantics BUILD

capabilities declares what the community turns on: video, live, shortform, store, tiers, embeds, offline_download (the signed transportPolicy continues to govern transport). Two-layer honesty, exactly the capability-status.ts pattern: DECLARED (owner turned it on, signed, gossiped) vs AVAILABLE (declared AND the runtime substrate exists). resolveBlockAvailability computes it; a declared-but-unavailable block renders its honest pending card. Safety and entitlement logic reason about a community from the manifest without reading content.

2.4 Layout editor BUILD

Mobile (tabs)/community/[communityId]/layout-editor.tsx, web ui/community/LayoutEditor.tsx, owner-gated. Same shape as theme-editor.tsx: a draft document in local state, live preview rendered through the REAL block registry (preview is the product), publish = one signed cm_layout revision. Per-block config sheets generated from each block's Zod schema. Shareable layout templates as meerkat-layout:v1: blobs over the existing deep-link + QR machinery, so "make my community look like a YouTube channel" is a paste.

Non-removable floors, enforced in the registry, not the editor: every community always exposes its channel list and settings, and any block presenting ranked content always renders the ranking picker with chronological present. A layout document cannot hide the honesty surfaces.

2.5 Parity and the auto-guard PHASE 0

  • Convert the parity script's core locks to a declarative CORE_TWINS registry (extending the chatKitTwins tuple shape), then add the missing meta-guard: enumerate data/*-core.ts, FAIL when a core has no lock entry (documented-exception list for channel-view-core and chat-compose, which legitimately diverge).
  • Lock the currently unlocked cores; reconcile join-flow.ts drift (real remediation).
  • Every new core in this plan lands with its lock entry in the same commit; the meta-guard makes forgetting impossible.

3. New channel kinds

Extend KNOWN_CHANNEL_KINDS from ['chat','library'] with: video, live, shortform, forum (posts-first presentation of the existing posts substrate), timeline (microblog with quote/repost), gallery, store, events, page. Each kind maps to a default block stack; the layout document can override per channel. Old clients render unknown kinds as the existing read-only banner; kind is inside the signed channel tuple, so tampering breaks the descriptor signature. Future per-channel fields (e.g. tierId) append to the channel tuple all-or-nothing, length-disambiguated, per the nested-append discipline.

4. Video VOD (YouTube parity)

4.1 Data model EXTEND

  • Schema migration (signed-row canonical append on library items): add thumb_wrapped_key TEXT (the anticipated "Phase 5" column) and extra_manifests_json TEXT to cm_library_items. The latter is an array of {label, contentCid, keyEpoch, wrappedKey, manifest, manifestSignature} covering renditions, caption tracks, and the filmstrip sprite. Extend the item-signature canonical bytes via conditional append (absent = legacy bytes; fixture-lock a legacy item). Extend collectBlobRefs (blob-transfer.ts:96) to walk the array so all sealed sidecars ride the existing session blob pipeline automatically.
  • metadata_json.video (inside the 16 KB curator-signed metadata; schema extension on movie/show/custom): chapters, captions meta, duration, default rendition.
  • Watch signals: new cm_view_events (shared_workspace, or_set): a SIGNED, opt-in "I watched this" event. Off by default per member per community. cm_library_progress stays personal and thin, preserving the property that a community cannot learn what you watched. The watch page shows "N members shared they watched", counted from verified events, never a fabricated views number.
  • Comments: a post thread anchored to the item (signed itemId anchor on the v2 payload), rendered by the existing chat kit. Likes: the existing reaction model. Up next: device-local queue (music sibling-queue pattern).

4.2 Playback and page EXTEND

watch-core.ts (pure, twinned) assembles the view model: rendition choice, caption cues parsed from WebVTT, chapter index, resume position, verified view count, honest availability line. Mobile watch page on the loopback server (dev build; Expo Go keeps the honest export-only fallback); captions rendered as our own overlay from parsed VTT cues (both surfaces, no native subtitle dependency); chapter markers and filmstrip scrub preview from the sealed sidecar. Web via the existing playbackPlan; rendition switch = plan re-evaluation. The video kind + video_gallery block render poster grids off thumb_cid/thumb_wrapped_key with duration badges from signed metadata.

4.3 Posters, filmstrips, transcode: where the work runs BUILD

The hard problem: transcoding requires plaintext; Meerkat's servers hold ciphertext. Three lanes, all producing the IDENTICAL sealed output shape so downstream code never knows where the work ran.

  1. Author device (default, ships first): poster + filmstrip via expo-video-thumbnails behind a new lazy dev-build seam data/video-frames-backend.ts (honest-null in Expo Go, the lan-backend.ts pattern); cover downscale finally implements the declared ResizeCover seam. No on-device full ABR: ffmpeg-kit is retired upstream and an on-phone transcoder is not currently defensible; a phone uploads its native rendition plus thumbnails.
  2. Author web/desktop (the real ladder): a WebCodecs transcode worker in meerkat-web (VideoDecoder/VideoEncoder + JS muxer) producing the fMP4 ladder client-side, sealed client-side. Plaintext never leaves author custody. The desktop browser becomes the creator studio, which is the right product shape anyway.
  3. Hosted, consent-gated FOUNDER-OPS: a transcode job on the hosted node for communities that already trust a hosted server with availability. The upload flow states explicitly that the server will decrypt to transcode; the key grant is a per-object DEK share, never the epoch key. Fail-closed when unconfigured. Lands last.

Honesty rule: a video with no ladder plays single-rendition decode-what-you-can, exactly as today, and the UI says so ("One quality available").

Live-only evidence: loopback playback + scrub on physical devices; large-file session-transfer soak between two devices.

5. Short-form vertical pager (TikTok parity) and the ranking-strategy interface

5.1 Pager BUILD

New feed item kind video in feed-core.ts; shortform-core.ts (pure, twinned) builds the pager queue, preload window (next 2 sealed items via the existing fetch path), autoplay eligibility, and mute state machine, with per-item "why" passthrough. Mobile: full-bleed snap FlatList, ONE loopback player mounted for the on-screen item only, mute-by-default tap-to-unmute, engagement row wired to the real reaction/comment substrate. Expo Go: honest poster cards with a "playback needs the full app build" notice, never a silent dead surface. Web: scroll-snap column on the MSE planner. Every number on the pager comes from verified rows; there is no view counter at all unless opt-in view events exist.

5.2 Ranking-strategy interface BUILD

  • feed-rank-core.ts (pure, twinned): FeedRanker over a FIXED feature set (kind, recency, unreadCount, replyCount, reactionCount, isFollowedAuthor, isSameCommunity). Built-ins: chronological (hard-wired, never removable), focused (today's KIND_RANK behavior, remains default), most_reacted, follows_first.
  • Community-authored rankers are DATA, not code: signed JSON weight vectors over that fixed feature set, carried in the layout document, clamped per-feature, schema-validated, fail-safe to chronological. No expression language, no eval, no fetch. The marketplace trades weight vectors; the client's fixed scorer runs them; the plain timeline is structurally always one tap away.
  • Persistence fix rides along: feed source toggles and the chosen ranker persist to mk_settings (today's toggles are useState-only, a verified gap).
  • The "why did I see this" sheet gains the active ranker's name and the item's feature values.

6. Offline: download manager, background pre-fetch, progressive watch

  • download-core.ts (pure, twinned) + device-local mk_download_queue (content_id, pin_context, priority, wifi_only|any, status, staged_blocks, total_blocks, timestamps). Progress = real staged-block counts from the store, never a synthetic percentage.
  • One-tap "Download to watch offline" = queue entry + pin class explicit on completion. Pause/resume: extend fetchAndPinFromHosts/loadFromRemote with per-chunk existence checks so a resume fetches only missing sealed chunks (brings the HTTP path to parity with blob-transfer's have-list).
  • Background pre-fetch: a runDownloadDrainJob composed into the existing runBackgroundSyncOnce round (same honest recorded-run pattern; OS scheduling stays dev-build-flag-gated exactly as today), plus an opportunistic trigger when a holder peer appears in a live session.
  • Progressive watch: playback permitted on a contiguous chunk prefix; makeChunkStream gains an honest stall at the first missing chunk (buffering UI + priority fetch), never silent gaps. Requires wiring the existing playback-hold registry into runLibraryEviction (a verified open gap) so LRU can never evict a file mid-play.
  • Local-only communities EXTEND: transportPolicy 'local_only' content already lives on device; download is instant and offline is the baseline. The owner toggle (signed revision through the existing field) + honest copy ships in Phase 1.

Live-only evidence: multi-hour download soak on device; eviction-under-pressure QA.

7. Multi-peer swarm and the seeder

Standardize on the sealed-share chunk model (the shipped one). The catalog piece model stays the live interchange for channel-history and the relay seeder catalog. The dead swarm classes are a design quarry, not a dependency: port rarest-first and piece bookkeeping onto the chunk model; retire publisher.ts/deep-link.ts fantasy URLs and fix the inaccurate BEP 19/Range docstrings in the same change.

Three deliverables, independently shippable:

  1. Parallel multi-host fetch BUILD: a chunk scheduler in remote-store.ts assigning missing chunks across all reachable hosts concurrently (bounded parallelism, per-host failover, verify-then-pin unchanged). No new wire protocol; immediate speedup wherever more than one host announces.
  2. Peer chunk exchange BUILD: extend blob-transfer.ts with BLOB_HAVE (availability bitmaps at session open for pinned contentIds in the shared workspace) and multi-peer scheduling with rarest-first selection, riding existing sessions over LAN/nearby/relay. Phones remain resolve-only to the open network (no inbound HTTP); phone-to-phone transfer happens only inside authenticated sessions, which is both the privacy posture and the NAT answer.
  3. Seeder deploy BUILD + FOUNDER-OPS: add meerkat-node.mjs to compose.production.yml with health checks; wire its existing announceHeldShareContent refresh loop; connect hosted-tenant pinning (the seeder_manifests table exists) so the $4.99/mo hosted server actually seeds its community's libraries 24/7. Copy stays "Available from members who have it, when a sync connects" until the seeder is live and probed, then upgrades to availability language backed by a real reachable-host probe.

Live-only evidence: 3+ device swarm session; seeder 24/7 soak; tampered-host negative on production infra.

8. Live broadcast (Twitch / YouTube Live parity)

The admission/roles/SFU substrate is built and verified; a default build has no rooms at all; nothing RTMP/egress/recording exists. Live is mostly a deployment-gated product build, not a protocol build.

  • live-core.ts (pure, twinned): broadcast state machine from REAL room events only; viewer count from real LiveKit participant events; stream health from real connection stats; moderation mapped to existing community roles.
  • Go Live: live kind + live_stage block. Host publishes; every member's join requests ['subscribe'] only (the admission request already carries requested permissions; isPermissionSubset permits requesting less than your role). Live chat = the channel's existing chat at the live-loop hot cadence, as an overlay.
  • Honest announces: an owner/host-signed going_live event (cm_live_announces, shared_workspace, lww, apply-time validated). "Live now" renders ONLY when a verified fresh announce exists AND the viewer's own join probe succeeds; never from the announce alone.
  • Record-to-VOD: LiveKit Egress writes the recording on operator infra; a live stage is NOT E2EE (the room banner already says so). The finished file enters the library through the normal sealing path (host device, or the consent-gated hosted lane); copy states who held plaintext.
  • Optional hardening: wire LiveKit frame-encryption events into the existing e2eeActive reducer (verified declared-but-unwired) for small symmetric rooms; large fan-out stays server-trusted and honestly labeled.
  • RTMP ingress (OBS) + HLS egress: LiveKit Ingress/Egress services. Code: ingest-key minting UI, egress trigger, imported-recording flow. FOUNDER-OPS: deploy Ingress/Egress + Redis + TURN (TURN also unblocks the verified STUN-only 1:1 call gap), capacity planning.

Live-only evidence: 2+ device broadcast, viewer-scale test, OBS ingest, recording round-trip. None of it claimable from tests.

9. Embeds (the external-content bridge)

  • embed-core.ts (pure, twinned) + embed block. An embed is authored as a sender-generated verified preview (the existing NC-2 link-preview pattern). The receiving device NEVER fetches the URL by default; the no-receiver-fetch rule holds.
  • Tap = explicit consent interstitial naming the destination ("This will connect you to YouTube and share your IP address with Google"), then webview or OS browser. Per-destination consent memory in device-local mk_embed_consent, revocable in settings.
  • Import-natively is the promoted path on the interstitial: for content the author owns, the flow routes into library ingest so the video becomes a sealed, offline-capable, P2P-distributable item. Embedding is the compatibility bridge; import is the real thing.
  • Privacy-proxy embed is designed but deliberately NOT sequenced: it shifts trust to the relay operator and adds abuse surface on operated infra; the consent gate + import already satisfy the honesty bar. Revisit only with founder sign-off.

10. Monetization: tiers, tips, storefront, payouts

Six wall constraints, verified in code review, binding on every item below: no joining column anywhere reachable from persona/device rows; credential and session bearer never on the same request; payment state account-side in aggregates only; no tier encoded in the platform credential (anonymity-set collapse); import-graph allowlist changes are reviewed one-line diffs; deletion copy stays honest about tax-retention records.

10.1 Membership tiers BUILD

  • A tier is a KEY LANE, not a flag: per tier, a child workspace (communityId:tier:<tierId>) with its own epoch chain via the existing commitMemberAdd/commitMemberRemoval. Tier channels sync under that key; non-payers structurally cannot read them. Lapsing = removal = epoch rotation; history follows the tier's historyScope.
  • Tier definitions live in the signed layout document; channel-to-tier mapping graduates to the descriptor channel tuple (nested append, §3) only if server-side enforcement needs it.
  • Purchase: web/hosted via Stripe Checkout on the existing billing service (the missing client purchase surface gets built here for both hosted-server and tiers); iOS digital-content tiers use IAP (RevenueCat) per App Store policy, with web purchase offered where policy allows.
  • Entitlement to key grant: payment settles on the ACCOUNT layer; the buyer's device presents a tier voucher (a per-community-tier blind-signed token from the billing service) to the community owner's device by mailbox; the owner device (or its delegated hosted node) commits the member-add to the tier workspace. Anonymity set = that tier's buyers, disclosed in copy (it is the same set the creator sees as "my subscribers"). No platform-wide credential ever encodes tier.
  • "Access granted" renders only after the key wrap row verifiably lands on the buyer's device.

10.2 Tips and one-time unlocks BUILD

Creator-directed one-time payments on the same rails: Stripe on web/hosted; on iOS, digital tips are IAP consumables, with the web path linked where allowed. A tip mints an optional signed, non-identifying supporter receipt the tipper may attach to a message (never automatic). Per-content unlocks reuse the tier machinery with a single-item key lane.

10.3 Storefront BUILD

  • store-core.ts (pure, twinned) + cm_store_listings (shared_workspace, lww, curator-signed: title, price, currency, digital|physical, checkoutRef, fulfillment descriptor, tombstone). The store block renders verified listings only.
  • Checkout: Stripe Checkout links minted by the hosted billing service per listing (physical goods are policy-clean on mobile; digital goods in-app on iOS route through IAP or are web-linked per current policy). Orders never become cm_ rows: order state lives on the billing service (account layer) and device-locally for the buyer; digital fulfillment = a sealed download grant (single-item key lane).
  • Payouts: Stripe Connect Express on the hosted billing service. Payout identity (bank, tax) is strictly account-layer; per-content earnings aggregate persona-side only as periodic totals crossing the wall under compute-use-discard.

Fix rides along: the verified boot-revalidation bug (_layout.tsx:99-109) that re-locks paid users on ANY network error is corrected to fail-open-to-cache on transient errors with a bounded revalidation window; fail-closed remains only on a definitive negative.

FOUNDER-OPS: Stripe Connect enablement + products, App Store IAP products, tax/counsel review (creator payouts are a regulatory step up; counsel is already the gating launch step), refund/dispute staffing. Live-only: end-to-end purchase, refund, revocation (epoch rotation on refund), and payout proofs on production rails.

11. Follow graph and discovery

  • Private follows stay as built (cm_public_follows, device-local, invisible to targets). Phase 8 finally consumes listPublicFollows: a Following feed source + the follows_first ranker.
  • Public follower registration (the first replicated social edge, deliberately server-side, not mesh-replicated): opt-in registration on the directory node, humanity-gated by the existing blind credential to keep counts sybil-resistant. Counts shown are distinct verified registrations, labeled "N registered followers"; the existing refusal to render fabricated totals is replaced by the real number only when the registry responds. Follower lists are never enumerable; creators see counts, not identities.
  • New-content notification rides the existing mailbox/push honesty path: a data-only wake enqueues a directory poll; a notification fires only after verified new content is actually fetched.
  • Discovery: the Discover tab grows directory browse (categories + trending frames already exist server-side), community cards from verified publications only, and the web invite deep-link listener + community/join route (verified missing on web) lands here for cross-surface invite parity.

Total code effort: roughly 26 to 34 engineering weeks, front-loaded so that after Phase 1 a community owner can already compose real interfaces from the blocks that exist today, and each later phase adds catalog entries without touching the spine. Sequencing rationale: the spine multiplies everything after it. VOD precedes short-form (player dependency) and transcode (pipeline dependency). Offline precedes swarm (the download manager is what makes multi-peer fetch observable). Live and monetization sit later only because both are gated on founder-ops (SFU deploy; counsel/Stripe/IAP) that can proceed in parallel from day one.

14. Honesty invariants carried through every phase (binding checklist)

  1. Every count (viewers, views, followers, seeds, progress) derives from engine events, sync_ tables, verified signed rows, or real store stats. No extrapolation, no placeholders.
  2. Every capability distinguishes implemented+tested vs dev-build-only vs founder-ops/deployment-gated, in capability-status.ts (which gains derived entries per phase) and in per-block availability copy.
  3. Staged is never sent; declared is never available; recorded is never delivered without a verified receipt.
  4. The receiving device never fetches sender-supplied URLs outside the embed consent gate.
  5. Every new pure core ships as byte-identical twins with a CORE_TWINS lock entry, enforced by the Phase 0 meta-guard.
  6. The two-identity wall constraints bind every money flow; the import-graph allowlists change only by reviewed one-line diffs.
  7. The plain chronological timeline is registry-enforced and cannot be removed by any layout document.
