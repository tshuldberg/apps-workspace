Meerkat · Community App Platform · Full-Ambition Feature Architecture

Communities as apps you assemble

The complete feature set required to let a Meerkat community builder compose any interface they want, video, galleries, live streams, forums, timelines, short-form, embeds, and reach functional parity with YouTube, Twitch, TikTok, Reddit, X, Discord, Patreon, and the rest. Grounded in the real code seams that already exist, honest about what must be built.

Date 2026-08-24 Companion to the full system & security review Posture Full ambition. No MVP framing.

The thesis in one sentence.

Meerkat should not ship a fixed set of screens that imitate other apps. It should ship a composition engine: a library of interface blocks (a video player, a live stage, a short-form pager, a forum, a timeline, a gallery, a store, an embed) that a community owner arranges into their own home and channels, backed by a content model that can be hosted, peer-to-peer, live, downloadable-for-offline, or local-only, per community, per block. When you assemble the right blocks, a Meerkat community is a YouTube channel, or a Twitch stream, or a subreddit, or a Discord server, or all of them at once. That is the product no incumbent can offer, because their business depends on owning the one interface you are allowed to use.

The five seams we build on

This is not a rewrite. Meerkat already has five load-bearing primitives that a composition platform plugs directly into. Understanding them is the difference between "build a new app" and "unlock the app we have."

Two more foundations matter: sealed content moves as verified blobs during sessions and file-requests (protocol/blob-transfer.ts), and every new capability ships as a pure logic "core" that is byte-identical across mobile and web, plus two thin screens, locked by the parity script. That delivery pattern is how everything below stays consistent across iPhone, Android, iPad, and desktop.

The composition platform

Four new pieces turn Meerkat from a fixed app into a platform. Each rides an existing seam.

1. The block registry BUILD

A runtime catalog mapping a declared block type to a contract: its props schema (Zod), its data source (which cm_ tables or blobs it reads), its capability requirements, and its renderer (a pure view-core plus mobile/web screens). This is the media type registry pattern generalized from "content types" to "interface blocks." A block is sandboxed: it can only read the data its contract declares, it cannot fetch arbitrarily, and an unknown block type renders a safe placeholder on older clients.

2. The layout document EXTEND

A new owner-signed descriptor field describing the community's home and each channel's composition: an ordered tree of blocks with per-block config. It is added through conditional canonical append, so it is invisible to legacy signature verification when unset and fully gossiped when set. A community owner arranging their home in the editor produces one signed descriptor revision. This is the same mechanism the channel organizer already uses for categories and layout, widened from a binary chat_first / library_first toggle to an arbitrary block tree.

3. The capability manifest BUILD

A signed declaration of which capabilities a community turns on: video hosting, live broadcast, short-form, commerce, offline download, external embeds, local-only storage. This gates which blocks are available, drives the honest "what this community can do" surface, and lets safety and entitlement logic reason about a community without inspecting its content. Capabilities that require deployed services (live SFU, always-on seeding) report honestly unavailable until those exist, exactly as capability-status.ts does today.

4. The community layout editor BUILD

The MySpace-grade authoring surface. It reuses the existing theme editor's shape (a visual editor over a signed blob, shareable by deep link and QR) and extends it: drag blocks onto the home, configure each, pick the storage mode, preview live, publish as one signed revision. The theme system already handles contrast enforcement and per-community styling; the editor adds structure on top of style.

Why this is the right shape: every hard part of a plugin platform, signing it so it cannot be forged, gossiping it so every member sees the same interface, theming it, scoping its data, moving its blobs, and degrading gracefully on old clients, already exists in Meerkat. The genuinely new work is the block registry and the layout composition model. Everything else is reuse.

The video VOD pipeline (YouTube)

Video-on-demand is the highest-leverage build because the hardest part is already done: the on-device loopback range server (data/loopback-server-core.ts) already streams encrypted video with per-chunk verified decrypt, real seeking over HTTP range, and no plaintext ever on disk. What is missing is everything around the player.

MKV and long-tail formatsBUILDRemux to a playable container at seal time (MKV is unplayable in browsers today).

The one real constraint: transcoding and frame extraction are heavy. On a hosted community server this is a background job. On a phone-only or local-only community it must happen on device (slower, or deferred), or the uploader's desktop seeder does it. The pipeline should be defined so the same sealed output is produced regardless of where the work ran.

Live broadcast (Twitch / YouTube Live)

Meerkat has symmetric calls and group rooms via a LiveKit SFU (real code, dev-build-only, unverified on device). The broadcast building block also already exists: the room membership model defines a viewer role that is subscribe-only. What is missing is the one-to-many product built on it.

What to build BUILD

  • Go Live mode: one host publishes audio/video/screen; viewers join as subscribe-only at scale using the existing viewer role. The SFU fans out.
  • Live chat overlay bound to the stream, on the existing chat kit and the live-loop cadence that already drives real-time channel updates.
  • Honest viewer count from real subscriber events, never a fabricated number, consistent with every other count in the app.
  • Ingress/egress: RTMP ingest so creators can stream from OBS; optional HLS egress for very large audiences; record-to-VOD that drops a finished stream straight into the community's video library as a sealed item.
  • Stream health, low-latency mode, raid/host handoff, moderation tools (slow mode, timeouts) reusing the community role and safety model.

Reality: live is deployment-gated. It needs a deployed LiveKit SFU with ingress/egress, TURN for NAT traversal, and two-device verification. The code path exists; the infrastructure and device proof do not yet. Copy must say "live" only when a real stream is connected.

Short-form vertical feed (TikTok / Reels)

This is a focused build on the existing feed. Today the feed is a card list with a closed set of item kinds and no video-first surface.

What to build BUILD

  • A vertical snap pager (full-bleed) with a new video-first feed item kind.
  • Viewport-driven autoplay: mount the loopback decoder only for the on-screen item, preload the next N, mute by default with tap-to-unmute.
  • Per-community and cross-community short-form sources, with the same source toggles and "why am I seeing this" transparency the feed already provides.
  • The pluggable-algorithm hook (see below) so a viewer can pick a ranking or keep a pure chronological pager.

The founder promise of "pick your algorithm, always keep a plain timeline" lands here and on the timeline block. The current feed ranking is already local, deterministic, and transparent, the ideal substrate. The build is a ranking-strategy interface: named, swappable rankers (chronological, most-reacted, a follow-graph strategy, a community-authored one) with the plain chronological option always present and never removable.

Offline download and async load

Your "download it, then watch end to end with no internet" requirement is closer than it looks. The data layer is already built: pin classes, per-library pin policy, a device storage budget with LRU eviction that only touches the fetch cache, and a "keep on this device" flag. Once sealed blocks are held locally, the loopback player plays the whole file offline.

What to build BUILD

  • A download manager UX: one-tap "download to watch offline," visible progress, pause/resume, a downloads queue, and wifi-only vs cellular policy.
  • A background pre-fetch trigger so a queued download proceeds when a holder is reachable, instead of only during a foreground sync.
  • Progressive watch-while-downloading for the sequential case (play the ranges you have while the rest arrives).
  • For local-only communities, this is native: content already lives on the device, so "download" is instantaneous and "offline" is the default. That is the dynamic nature you described, a community whose storage mode makes offline the baseline rather than a feature.

The content modes: hosted, P2P, live, local-only

The same video can be delivered four ways, and a community (or a block) chooses. This dynamism is what makes Meerkat different from any single incumbent.

ModeHow content movesStateFeels like
HostedAn always-on seeder / hosted server holds and serves sealed blobs; discovery via the zero-knowledge host registry.BUILD deploy seederYouTube: always available.
Peer-to-peer (torrent-style)Multi-peer swarm download from everyone who has it; parallel pieces, rarest-first. The full swarm stack is written but not wired to the app.BUILD wire + seedBitTorrent: resilient, no central host.
LiveSFU fan-out from the broadcaster to viewers in real time; optional record-to-VOD after.BUILD deploy SFUTwitch: watch it happen.
Local-onlyContent never leaves the device except over a direct session with an invited peer. Scope caps already enforce this.EXTEND add toggleA private vault / LAN Plex.

The multi-peer swarm is a notable near-win. A complete torrent subsystem (swarm manager, rarest-piece downloader, piece manager, web-seed client, magnet publisher) already exists in the sync package but is not consumed by the app; the app currently does sequential single-host fetch. Wiring the swarm into the fetch path, adding a peer transport for phone-to-phone piece exchange, and deploying an always-on seeder turns "sealed-share fetch" into true torrent-style distribution for large video. Phones stay resolve-only for the open network (no inbound HTTP), so the always-on seeder is the piece that makes hosted availability real.

Embeds and external content (the YouTube question, honestly)

You asked for YouTube content displayed directly, both hosted-on-Meerkat and embedded-from-YouTube. Native hosting is the video pipeline above. Embedding a live YouTube player is where an honest tension appears, and it is worth stating plainly because it touches Meerkat's core privacy promise.

The conflict: Meerkat has a strict rule that a receiving device never fetches from a URL a sender supplied (link previews are generated by the sender and shipped as a verified image blob; the receiver only renders it). Embedding a real YouTube player breaks that rule: every viewer's device would connect to Google's servers, handing Google each viewer's IP address and watch signal, the exact tracking Meerkat exists to escape.

The three honest options BUILD

  1. Consent-gated embed (recommended default for embeds): the embed block shows the sender's static thumbnail and title; tapping it presents an explicit "this will connect you to YouTube and share your IP with Google" consent, then plays. Privacy stays opt-in and informed.
  2. Privacy-proxy embed: route the fetch through a Meerkat relay so Google sees the relay, not the viewer. Adds infrastructure and shifts (not removes) trust to the relay operator.
  3. Import, do not embed: a creator who owns their video hosts it natively on Meerkat as a sealed library item, gaining offline, P2P, and true privacy. This is the path that best serves the vision; embedding is the compatibility bridge for content that lives elsewhere.

All three should exist, with import as the promoted path and consent-gating as the floor for any real external fetch. The block is honest by construction: it never silently phones home.

Creator monetization and commerce

These are greenfield pillars, but the primitives to gate access already exist (signed roles, epoch keys as read capability, membership tiers as key-holder sets, the entitlement/blind-credential layer).

  • Membership tiers (Patreon/Twitch subs) BUILD: paid tiers that grant the epoch key for tier-gated channels and content. Membership is already the read capability in the crypto model; a paid tier is a membership whose grant is gated on a payment.
  • Tips and one-time unlocks BUILD: the pay-to-post and app-unlock rails already prove the payment plumbing; extend to creator-directed payments.
  • Commerce / storefront BUILD: a store block with listings, checkout, and fulfillment for digital goods (sealed downloads) and physical goods.
  • Payouts BUILD: creator payout accounting on the hosted billing layer.

Honesty and safety constraints carry over: real receipts only, fail-closed entitlement, and the account/identity wall stays intact (a paying viewer's account identity never links to their mesh persona).

A build sequence that keeps every step shippable

Full ambition does not mean unordered. This sequence front-loads the platform spine and the highest-leverage media build, so each phase produces something a community can actually use.

  1. Platform spine: block registry + layout document + capability manifest + layout editor. Ship with the blocks that already exist (forum, chat, gallery, files). A community can now compose an interface today.
  2. Video VOD: watch page + thumbnails + transcode/ABR on top of the loopback decoder. The video and gallery blocks go live. This is the YouTube core.
  3. Offline download manager + local-only mode: the download UX and the community storage toggle. Plex-style and "watch offline" land.
  4. Short-form pager + ranking strategies: the TikTok surface and the pick-your-algorithm / always-plain-timeline promise.
  5. P2P swarm + hosted seeder: wire the existing torrent stack and deploy the always-on seeder. Hosted and torrent-style availability become real.
  6. Live broadcast: Go Live on the SFU with viewer fan-out, live chat, record-to-VOD. Twitch/YouTube-Live. (Gated on SFU deploy + device proof.)
  7. Monetization + commerce: membership tiers, tips, storefront, payouts. Creators can earn.
  8. Timeline block + follow graph + discovery: the X/Twitter surface and the connective tissue that makes creators findable.
  9. Embeds: the consent-gated external-content bridge, with import promoted as the privacy-preserving path.

The bet. No incumbent can give a community owner a video channel, a live stream, a subreddit, a Discord, a store, and a private local-only vault in one composable, end-to-end-encrypted, no-algorithm-unless-you-choose-one surface, because their entire business is owning the one interface you are allowed to use. Meerkat's architecture was, perhaps accidentally, built to make exactly this possible: signed portable descriptors, forward-compatible channel kinds, a fail-safe theming model, content-addressed sealed media, and four delivery modes for the same bytes. The composition platform is the feature that turns all of that into the product you described.
