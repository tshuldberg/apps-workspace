## 3. Lessons learned

- **EXPO_PUBLIC inlining contract:** an `EXPO_PUBLIC_*` value exists in a release bundle only where the source contains the literal member expression `process.env.EXPO_PUBLIC_NAME`. Captured objects, destructuring, and dynamic keys silently return undefined in TestFlight/production while working in dev, Expo Go, and Vitest. Check this first for any "works locally, unconfigured in TestFlight" symptom. Web (Vite) has the same rule with `import.meta.env.VITE_*`.
- **Navigation and RN modals do not mix in one commit.** Never unmount a visible RN `<Modal>` (toggle `visible`; remount via a per-open counter key while hidden if fresh state matters), never navigate imperatively, present a second Modal, or fire an `Alert.alert` while one is dismissing (an Alert is a native modal presentation and hits the same race). The accepted fix shape: queue the action in a ref/state, flush from Modal `onDismiss` (iOS-only in RN 0.81) plus a Platform-gated visibility effect (Android unmounts Modal children the instant visible flips false). A dismissal-flushed queue must live in a component that SURVIVES the dismissal; when a host wraps the queueing sheet in its own Modal, the HOST owns the queue (InvitePreviewSheet onNavigate override + OnboardingGate shape). When a shared kit sheet's callbacks may alert/navigate (delete/report confirms), put the queue INSIDE the kit sheet so every consumer is fixed at once (MessageActionsSheet shape). Sweep pattern: grep every `<Modal` screen for `setXOpen(false)` adjacent to `router.`/`Alert.alert`/another `setYOpen(true)`, and for `{show ? <Sheet visible` conditional mounts.
- **try/finally without catch is the recurring "tap does nothing" bug, and it clusters in file pipelines.** `finally` resets busy so the UI looks idle while the rejection vanished; worse, an await BEFORE the try (blob read, destination prompt) skips the finally too and strands the busy label forever ("Saving…"). Every async handler needs a catch that renders an honest failure; the awaits belong INSIDE the try; batch loops catch per item so one throw cannot eat the partial result. Sweep the WHOLE file including mount/boot effects, interval callbacks, and fire-and-forget `void promise` calls - a `void` without `.catch` is the same bug in a different jacket. Verify the deep seam too: provider methods that LOOK result-union can still throw (queueFileGrant's buildFileGrant blob reads).
- **A "pure resolver" helper with try/finally still propagates.** A shared `resolveX` awaited inside a caller's for-loop kills the whole loop with one rejection; make the resolver itself fail-safe (catch -> null) when null is already its honest miss value, and lock the catch COUNT when the file has several such blocks (CORE_TWIN: edit both surfaces identically).
- Success copy ("Copied", "Sent", "Saved") is claimed only AFTER the await that makes it true resolves; a try/catch around a `void asyncCall()` protects nothing. Web `navigator.clipboard.writeText` and mobile `Clipboard.setStringAsync` genuinely reject.
- **Domain rules must be swept PER SURFACE and PER ENTRY POINT, not per feature, and "read-only" means EVERY write verb.** "Archived channels are read-only" held on the mobile channel composers and nowhere else: not on web (whole surface missing the check), not in post threads (a reply back door), and even after the composer fix, reactions, edits, deletes, and ROOM JOIN still wrote into archived channels. Enumerate every affordance that writes into the state (chat/post/thread composers, sheet Reply/React/Edit/Delete, hover quick-reacts, emoji pickers, add-reaction chips, sticker sticks, room entry) on BOTH surfaces, and gate the affordances rather than letting them dead-end into a hidden composer (a sheet Edit that fills a hidden composer is a dead tap plus stale editing state). Accepted read-only rendering: existing reaction chips stay VISIBLE (they are preserved content) with taps inert via ONE gated toggle choke point; pure-write affordances (hover bars, "+" hosts, Edit/Delete) are hidden; device-local actions (Copy, Report) stay. Thread the state into pure entry resolvers (room-entry `archived` -> honest reason) instead of screen-side special cases.
- **Error surfaces must live in the pane the user is looking at.** A shared `channel.error` rendered only inside the chat pane is invisible while the Posts pane is active (`display:none` siblings keep state but also hide failures). Every visible segment needs its own honest failure surface for shared error state.
- Back affordances need `router.canGoBack()` with a fallback route on EVERY deep-linkable screen; fall back to the nearest sensible parent (community home for channel/files, the channel for a thread/room), not always the tab root; a locked-state fallback must target a FREE route.
- **Controls must toggle off observed state, never hardcode the "on" direction.** `setMic(true)` can never mute and silently overclaims; derive the next value from the reduced local-participant truth, catch the (permission-denial) rejection, and let the label reflect the real state. Prefer an inline error line over window.alert for control failures.
- When one row has several action buttons sharing a flow, busy state needs a per-action dimension (`{id, decision}` / `busy: 'approve' | 'decline' | null`), or every button claims the in-flight verb.
- Cross-surface drift hides in half-applied hardening: diff the twin the moment you find a bug once (delete-confirm existed in web ChannelView but not web PostThreadView; the draft stash existed in the mobile channel screen but not the mobile thread). Also check both surfaces for the same class immediately.
- Fail-closed rendering: an error state must not resurrect affordances the failure just proved impossible; selection/target state must self-repair when its referent disappears; a "you need X first" notice keys on what is actually offered.
- Multi-step sequential mutations over a device list need single-flight + a partial-failure notice.
- A parity-locked string is changed by updating the surfaces AND the lock needle in `scripts/check-meerkat-parity.mjs` in the same change; ADDING a locked string to a new surface (web archived banner) is free and strengthens the lock. Em dashes are banned even in UI copy.
- Guard tests that scan source are the accepted way to pin screen wiring: scope regexes to the exact pattern, count occurrences to pin "all N handlers have it", and pin structural absences (`not.toContain('setMic(true)')`).
- Repo idiom: screen logic goes in a pure `data/*-core.ts` with unit tests; every new mobile core needs a `CORE_TWINS` entry or exception line in the parity script in the same change. Editing an EXISTING core twin means byte-identical logic edits on both surfaces below the anchor.
- Billing/entitlement truth: mobile `data/app-unlock.ts` + gate in `(root)/_layout.tsx`; web `lib/hosted-access.ts` + `AppUnlockSection.tsx`. Price never hardcoded ($4.99 one-time + $4.99/mo hosted, founder-locked). A "connection server" is the wss relay; the hosted billing service is `MEERKAT_HOSTED_API_URL` (https); never conflate them in copy.
- Live-testing the web app locally: Vite with `VITE_MEERKAT_HOSTED_API_URL` at a scratchpad stub answering `GET /api/entitlements/meerkat-app` `{"unlocked": true}` (CORS `*`), then the real "Restore purchase". Do age gate + onboarding + restore in ONE uninterrupted session. NEW hazards observed this session: (a) the FIRST boot after a wipe can come up with the orphaned signing key ("Sync signing private key is unavailable in secure storage.") even with no server restart - wipe again and redo; the very first wipe can also be blocked by the open DB connection ("Meerkat could not start." once); (b) clicking a NAME input can summon a password-manager extension popup that steals window focus and blocks ALL browser tools with "Cannot access a chrome-extension:// URL" - recover by re-navigating the tab, and avoid focusing name-like fields (keep default values). Never click paths that call window.confirm/alert during automation; source-lock those instead. The iOS Simulator has no tap driver; mobile interaction checks are founder device checks.
- A background persist loop that retries immediately on failure turns a permanent failure into a silent hot loop with memory-only data (browser-secret-store: 10k identical warns; secrets lost at reload). Failures need backoff, a cap, and an honest surface; create-if-absent of a shared crypto key must run under the same lock as the writes it protects.
- A catch that maps every failure to a default state can hide a broken precondition; distinguish precondition failures (surface an error) from the genuine negative result. Change-notification seams that skip byte-identical writes fire NO listeners on a re-validate producing the same value.
- `HonestNotice` (mobile kit.tsx) takes `tone: 'info' | 'warning' | 'danger'`; blockers must not use the default green. `markOnboardingComplete` fires listeners synchronously inside the caller's handler.
