## 3. Lessons learned

- **EXPO_PUBLIC inlining contract (the big one):** an `EXPO_PUBLIC_*` value exists in a release bundle only where the source contains the literal member expression `process.env.EXPO_PUBLIC_NAME`. Captured objects, destructuring, and dynamic keys silently return undefined in TestFlight/production while working in dev, Expo Go, and Vitest. Any "works locally, unconfigured in TestFlight" symptom should be checked against this first. Web (Vite) has the same rule with `import.meta.env.VITE_*`.
- Billing/entitlement truth: mobile wrapper `app/(root)/data/app-unlock.ts` (sole importer of react-native-purchases; unlock derived only from store CustomerInfo via `deriveMeerkatAppUnlock`); gate at `app/(root)/_layout.tsx` via `isMobileAppUnlocked(db)`; cache keys in `app-unlock-keys.ts` are hints revalidated on launch. Web: `src/lib/hosted-access.ts` + `AppUnlockSection.tsx`. Price never hardcoded; falls back to `@mylife/billing-config`.
- `check-build-env.mjs` enforces store keys and https endpoints only for `EAS_BUILD_PROFILE === 'production'`. A testflight build can legitimately ship without hosted endpoints; runtime copy must stay honest about it.
- Vocabulary: a "connection server" is the wss relay (`MEERKAT_DEFAULT_RELAY_URL`); the hosted billing/link/entitlement service is `MEERKAT_HOSTED_API_URL` (https, `extra.hostedApiUrl`). Copy that conflates them makes false claims when one is configured and the other is not.
- `HonestNotice` (mobile kit.tsx) takes `tone: 'info' | 'warning' | 'danger'`; blockers must not use the default green. Web's HonestNotice already styles as warning.
- Fail-closed rendering rule: an error state must not resurrect affordances the failure just proved impossible. Route failures through a phase decision that consults `isPurchasesConfigured()`.
- Repo idiom: screen affordance logic goes in a pure `data/*-core.ts` with unit tests; every new mobile `data/*-core.ts` must get a `CORE_TWINS` entry or a `CORE_TWIN_EXCEPTIONS` line in `scripts/check-meerkat-parity.mjs` in the same change or parity fails.
- None of the upgrade/AppUnlockSection copy edited here was parity-locked, but always grep `scripts/check-meerkat-parity.mjs` for a string before changing it; compose/public unlock-sheet strings ARE locked.
- Guard tests that scan source (`expect(source).not.toMatch(...)`) are the accepted way here to pin screen wiring that has no render-test harness; scope regexes to the exact pattern (a blanket `not.toContain("setPhase('error')")` broke on a legitimate use, and a comment mentioning `<Redirect>` broke a blanket `not.toContain('<Redirect')`).
- **Navigation and RN modals do not mix in one commit.** Never unmount a visible RN `<Modal>` (toggle `visible` and let the native dismissal finish), never navigate imperatively while a modal is dismissing (queue and flush in `onDismiss` on iOS, a visibility effect on Android), and never guard a route by returning `<Redirect>` in place of the layout's own `<Stack>` navigator when the target lives inside that navigator (use an effect-driven `router.replace` that keeps it mounted). Violating all three at once is what froze the app.
- `markOnboardingComplete` fires its listeners SYNCHRONOUSLY inside the caller's event handler: every subscriber (including AppStack's gate) re-renders in the same commit as whatever the caller does next. Know this before adding side effects around it.
- "Tap does nothing" has two very different causes here: an unhandled promise rejection killing the handler silently (fix: try/catch in every store-action handler), or the tap never reaching the button because a stale native window is eating touches (fix: the modal rules above). A whole-app freeze points to the second.
- An entitlement gate replace can make the gated screen the stack's ONLY route: every back affordance on such a screen needs a `router.canGoBack()` fallback, and the locked fallback must target a FREE route (/discover) or the gate bounces it straight back.
- Web checkout is redirect-shaped: any `success_url` state (like `?unlock=success`) must be consumed on return, confirmed server-side, and stripped from the URL; the param is forgeable and is never itself an entitlement.

## 4. Next session briefing

You are debugging a Meerkat billing/unlock issue. Before code: reproduce the reported state against the phase machine in `upgrade.tsx` and decide which phase the user was actually in; most "impossible" screenshots are a legal but wrong transition (issue 2 above was tapping Restore from unavailable). Check build vintage first: which commit was the installed build cut from, and does its eas.json profile env match assumptions? Trust `git log -- <file>` over memory. Root cause before any fix; a green dev environment proves nothing about a release bundle where env inlining is involved.

For a hang or freeze report, do not stop at the tapped button: walk the whole navigation path the user took (gates, modals, redirects) and look for the three-way race in Lessons learned (modal unmount + imperative nav + navigator swap) before blaming a native SDK call. A wrapper like `purchaseAppUnlock` that returns Result on every path cannot hang the UI; the UI freezes when touches stop arriving.

Then, before finishing, sweep ADJACENT components, blocks, and sections of the same page (and its web twin) for related issues: every button that can only fail, every notice tone, every dead message path, every state string that could overclaim, every back affordance that can dead-end, and every checkout/return seam.
