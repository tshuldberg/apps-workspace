## 2. Resolution report

### P0 fix (browser-secret-store + boot + unlock machine)

- `apps/meerkat-web/src/lib/storage/browser-secret-store.ts` (rewritten): (1) key create-if-absent runs under the SAME lock discipline as vault writes: a module-level in-process mutex chain (covers same-realm concurrency and lock-less environments) composed with the origin-scoped `navigator.locks` Web Lock; the whole boot read (key load/create + vault read + decrypt) is ONE lock acquisition. (2) Every vault record is stamped with the `id` of the wrapping key that encrypted it (`WrappingKeyRecord { key, id }`; legacy bare-CryptoKey records upgraded in place), so key-vs-vault mismatch is detected deterministically. Boot throws typed `SecretVaultUnreadableError` (`key_mismatch` / `decrypt_failed` / `signing_key_missing`) instead of a raw OperationError. (3) Persist failures back off exponentially (500 ms to 30 s cap) via a scheduled retry, never a tail-call; after 3 consecutive failures an honest persist-failure surface activates (`getPersistFailure()` + `subscribePersistFailure()`); a mid-session re-key (wipe raced a live instance) is FATAL: one warning, surfaced honestly, never retried, and never clobbers the other session's vault. (4) The merge SNAPSHOTS the write-authority sets and restores them on failure, so a failed persist can never silently drop pending writes (found by the new regression test, not inspection). (5) Vault + key record are written together in one IndexedDB transaction (`idbPutMany`, new helper in `idb.ts`), so a wipe raced by a live persist leaves key+vault consistent instead of a vault no stored key can open. (6) `flush()` now REJECTS when the attempt failed, so MK-001 durability-critical callers fail loudly (all callers audited; fire-and-forget sites got catches).
- `apps/meerkat-web/src/lib/browser-sync-init.ts`: boot is a single-flight PROMISE cache (StrictMode's double-mounted effect shares one boot; a rejected boot clears the cache for retry).
- `apps/meerkat-web/src/lib/MeerkatProvider.tsx`: `resolveOrCreateIdentity` detects identity-row-without-signing-key and throws the typed error; the boot catch routes `SecretVaultUnreadableError` to a new honest `BootRecoveryScreen` ("Meerkat cannot read its keys in this browser": what happened, what is lost, what is not, recovery-key path, `Reload and try again` + confirmed `Start fresh in this browser` that awaits `deleteDatabase` and preserves localStorage so a purchase grant survives); non-Error throws now render `String(error)` instead of the messageless wall; the secret-store persist failure renders as a fixed top banner while the app runs.
- Unlock machine (issue 4): the validator moved INTO MeerkatProvider as a seq-guarded 4-state machine (`checking` / `unlocked` / `locked` / `cannot_verify` with honest detail + `revalidate()`), validated once when boot lands and ADOPTING (never re-fetching, loop-free by construction) on cache notifications, which fire on every `setCachedAppUnlock` including byte-identical writes (`hosted-access.ts`). `App.tsx` and `AppUnlockSection.tsx` both consume `m.appUnlock` (the section holds NO local unlocked state; `stripe-return-honesty.test.ts` re-pinned to the new invariant), and the locked shell renders `cannot_verify` as "Purchase could not be verified" + Try again instead of the not-entitled pitch. `appUnlocked` gating (auto-connect, storage schedules) now follows the VALIDATED state.

## 3. Lessons learned

- **Create-if-absent of a shared crypto key must run under the SAME lock as every write it protects, and the key's identity must be stored so a mismatch is detectable.** A read-then-create without a lock mints two keys under any concurrency (StrictMode, a second tab, a wipe race); stamping records with the id of the key that wrote them turns an undecipherable OperationError into a deterministic, typed, recoverable half-state. Pair it with a single-flight PROMISE cache on the boot path: caching only the resolved value still runs N concurrent boots.
- **A background persist loop that retries immediately on failure is a hot loop; and clearing write-authority state BEFORE the write commits silently loses data on failure.** Failures need exponential backoff, a surface threshold, and an honest banner; authority sets get snapshotted per round and restored on failure; a provably-permanent failure (re-keyed store) is FATAL: surface once, never retry, never overwrite the other session's data. `flush()` must REJECT on a failed attempt so durability-critical callers fail loudly. And a read-merge-adopt cycle over a shared record must never adopt the stored base over a key with a PENDING local write: any write that lands between the round's snapshot and its merge would otherwise be reverted to the stale base in memory and then persisted stale (Set-6 review item 16).
- **Boot half-states deserve a RECOVERY SCREEN, not an error line.** Detect them typed (undecryptable vault, identity row without its signing key), and render what is lost, what is not, and the real options (restore-from-backup path, confirmed start-fresh with an AWAITED wipe). A messageless fallback for non-Error throws is a bug: always derive a description (`message || name || String(error)`).
- **One validated state machine, one consumer surface.** The unlock split-brain came from three independent validators over one cache. Distinguish checking / verified-yes / verified-no / CANNOT-VERIFY (fail-closed but honest, with retry), put the machine in the provider, and have every surface read it. Change-notification seams must fire on every authoritative answer, including byte-identical ones; make re-validation loop-free by ADOPTING in-session server answers instead of re-fetching on notify.
- **A destructive flow may navigate away ONLY on real success.** `finally { navigate }` after a revoke/disconnect/delete shows the failure alert mid-navigation (modal race family) and leaves the world looking like the action happened. Track `succeeded` and gate the navigation; the failure message must say "Nothing was disconnected."-style truth.
- **Every mutating storage/backup/restore/connect flow needs a synchronous single-flight ref; state-based busy flags have a re-render gap.** And every selection over a FILTERED list needs stale-selection repair: re-derive the effective target against the current filtered truth, never `selected ?? first`.
- **Clipboard, share-sheet, SAF picker, secure store, signing, and account flows are genuinely-throwing seams; claim success only after the await resolves.** "Copied"/"Saved" set before the promise resolves is fake success; a missing API (no `navigator.clipboard`) must say so, not no-op. But verify at the seam first: this repo's client cores overwhelmingly fold network+json to result unions (probe/load/submit/export/acquire families) and adding catches there is noise. DB k/v get/set stays the trusted bare idiom. try/finally without catch is the recurring "tap does nothing" bug; busy/loading resets belong in finally; a read-model `.then(set)` needs a catch that either renders an honest error or deliberately keeps the last REAL state (documented).
- **A dropped result union is a dead tap** (`if (id) navigate;` with no else); render every branch. A wizard phase that can be entered before its data exists must have an escape: on a setup throw, fall BACK to the phase whose panel renders the error and the retry.
- **Navigation, Alerts, and RN modals do not mix in one commit.** Never unmount a visible `<Modal>`, navigate, present a second Modal, or fire `Alert.alert` while one is dismissing. Queue the action in a ref and flush from Modal `onDismiss` (iOS) + a Platform-gated visibility effect (Android). The hazard hides behind seams (provider methods, shared-sheet callbacks, and now `finally`-navigation under an error Alert). In-sheet two-step confirms (Delete > "Delete forever" / "Keep it") avoid stacking an Alert on a Modal entirely.
- **Back affordances need `router.canGoBack()` with a fallback on EVERY deep-linkable screen, including screens that are deep-link TARGETS (theme import) and SHARED headers** (one bare back in a shared header is five broken screens); a screen reached via `replace()` may have no back affordance at all; check both.
- **Any async result applied to state needs a supersede guard when the input can change underneath it** (seq refs on probes and validators); auto-close/auto-back timers must be owned (cleared on unmount) and verify their target is still current.
- **Error surfaces must live in the pane the user is looking at**; a state set but never rendered is the same bug one step later (lint's no-unused-vars caught one live; treat that warning as a correctness signal).
- Domain rules must be swept PER SURFACE and PER ENTRY POINT ("read-only" means every write verb incl. pickers/intake/deep links); re-derive enable predicates from filtered truth; controls toggle off observed state; fail-closed rendering never resurrects affordances the failure disproved; stale selection/pick state self-repairs when its referent disappears.
- Cross-surface drift hides in half-applied hardening: diff the twin on every find (this set: the disconnect finally-navigation, the stale backup target, the one-tap theme delete, and the clipboard family all existed on BOTH surfaces).
- Plan 51 wall holds: account flows never touch the mesh identity; screens calling account-core catch their throws with copy that never fabricates signed-in/verified/entitled/deleted; `cannot_verify` never renders as not-entitled.
- **EXPO_PUBLIC / VITE env inlining contract:** values exist in release bundles only as literal member expressions (`process.env.EXPO_PUBLIC_X`, `import.meta.env.VITE_X`); captured objects and dynamic keys silently return undefined in production while working in dev and tests.
- **Programmatic form fills are not user input.** The "age gate needs two clicks" report reproduced only with scripted fills that skipped the auto-advance input events; with real typing it passed first-click. Verify input-driven bug reports with REAL typing before changing product code.
- A parity-locked string changes by updating surfaces AND the lock needle in `scripts/check-meerkat-parity.mjs` in the same change; ADDING strings is free; byte-identical/anchored core twins are edited on both sides or not at all. Em dashes are banned even in UI copy. Guard tests that scan source are the accepted way to pin screen wiring; make each lock fail on revert for the right reason. Repo idiom: screen logic goes in a pure `data/*-core.ts` with unit tests; every new mobile core needs a `CORE_TWINS` entry or exception.

Age gate (real typing) + onboarding + restore in ONE session; close stale app tabs first and AWAIT every `indexedDB.deleteDatabase` (onsuccess/onerror/onblocked) before reloading; never click window.confirm/alert paths in automation (source-lock them); the iOS Simulator has no tap driver, so mobile interaction checks are founder device checks.
