# mynews runtime contracts

Preserved from `MyLife/apps/mynews/CLAUDE.md` during the September 5, 2026 instruction reset. Paths in the retained text are relative to the originating project/package unless stated otherwise. Dated rollout notes are historical evidence, not current readiness claims. Consult the relevant contract when changing its implementation; generic agent workflow is governed by AGENTS.md.

## Provider tree (`app/(root)/_layout.tsx`)

`DatabaseProvider > AuthProvider > SubscriptionProvider > CloudProvider > IdentityProvider > TermsGateProvider > PremiumGate > Stack`.

- `providers/DatabaseProvider.tsx` (`useMyNewsDb`): opens `mynews.db` (expo-sqlite), runs `MYNEWS_MODULE.migrations` up statements version-gated by `PRAGMA user_version` (V1 is idempotent DDL).
- `providers/CloudProvider.tsx` (`useMyNewsCloud`): `{ isConfigured, port, reason }`. `port` is `createMyNewsCloudAdapter(config)` only when `getMyNewsCloudConfig()` succeeds; otherwise `null`. There is no in-memory or demo adapter in the runtime path.
- `providers/IdentityProvider.tsx` (`useMyNewsIdentity`): loads or generates one device Ed25519 author identity via `@mylife/sync`, persisting `{ publicKey, privateKeyHex, createdAt }` JSON in expo-secure-store under `mynews.identity.v1`. Returns `{ pubkeyHex, privateKeyHex } | null` while loading. `useMyNewsIdentityActions()` adds `generateCandidate()` (mint a keypair without installing it) and `installIdentity()` (persist, then swap). Rotation and recovery MUST mint first, get the server to accept the transition, and only then install: installing early would leave the device holding a key the chain does not know, unable to publish.
- `providers/SubscriptionProvider.tsx` initializes RevenueCat through `@mylife/subscription`, resolves the MyNews entitlement, and exposes purchase, restore, and refresh. Missing configuration renders the explicit unavailable state and no purchase controls.


## Honesty boundary (Critical)

- `data/launch-environment.ts` `getMyNewsCloudConfig()` reads `EXPO_PUBLIC_MYNEWS_SUPABASE_URL`, `_SUPABASE_ANON_KEY`, optional `_FUNCTIONS_URL`; trims, requires https, strips trailing slashes.
- When unconfigured: Today, article, and journalist screens render honest not-connected copy; the composer keeps Publish disabled with plain copy. No fabricated feeds, no simulated success.
- Publish never fakes success: `publishDraft` typed error codes map to inline copy via `lib/publish-errors.ts`. On success the local draft is deleted and the article opens.
- Follows are device-local (`nw_follows`); they only shape the Today feed and are labelled as such.

- Account rights (plan 48 WP5): `app/(root)/account-delete.tsx` and `app/(root)/account-export.tsx`, reached from the Me tab. Deletion needs the phrase `DELETE MY ACCOUNT` typed exactly and a recent sign-in (`reauth-required` offers a sign-out-and-return path), then shows a countdown and a cancel button for the whole 7-day grace window. Per-step outcomes render verbatim, so a `skipped-unconfigured` step reads "Not configured on this server" and never as done. Export builds the JSON in memory and hands it to the share sheet; view-model logic is pure in `app/(root)/lib/account.ts`.
- Key custody (plan 48 WP6): `app/(root)/keys.tsx` ("Keys and Recovery", reached from the Me tab) is the whole custody surface: the public key chain, recovery-kit create/export/escrow/import, rotation, per-device revoke, and the state of any recovery in flight. View-model logic is pure in `app/(root)/lib/keys.ts`; flows live in `@mylife/mynews` (`data/key-custody.ts`) and crypto in `signing/recovery-kit.ts`.
  - Losing a signing key is no longer terminal for a byline. It used to be: the journalist could still sign in but could never publish another revision of their own work. Recovery is either a kit (their own encrypted copy of the key, openable ONLY by a 160-bit code they hold) or another device that still holds an active key.
  - The server never holds openable key material. Escrow stores secretbox ciphertext; the recovery code never leaves the device. Every escrow write and read, allowed or denied, lands in an owner-visible access log, and a key bind within 24h of a read is published as a public "restored from encrypted backup" event, so a quiet restore is impossible.
  - Recovery WITHOUT a kit is HARD-DISABLED and must stay that way until a notification provider ships. It depends on delivering a notice carrying a keyless cancel token, which is the only thing that lets a real owner stop a stolen-session takeover. `custodyPosture`/`noKitRecoveryCopy` render it as unavailable WITH the reason. Never present it as available, and never fake or queue a notification.
  - Nothing installs a rotated key locally before the server accepts it, and nothing reports success it cannot see in the envelope. A revoked signer gets the typed `key-revoked` (never `bad-signature`, which would be false) and routes to this screen from the composer and the draft publish path.
  - Readers verify too: `article/[slug].tsx` re-checks every revision signature and binds it to the byline's chain via `verified_key_id`, badging pass, caveat, or failure. Verification NEVER depends on wall-clock: a revision signed by a key that was later rotated away still verifies, because revocation stops new writes rather than rewriting the record.
- Entitlement-exempt routes (plan 48 WP7): `PremiumGate` wraps the whole `(root)` Stack, so the exemption list in `app/(root)/lib/entitlement-routes.ts` is what keeps obligations reachable in an unentitled or unconfigured build: `legal` (and every `legal/*` document), `notices`, `account-delete`, `account-export`. Matching is whole-segment on the first non-group segment, group segments like `(root)`/`(tabs)` are skipped, and the list is pinned against the registered `Stack.Screen` names by a test. The gate decision itself is the pure `premiumGateView` in `app/(root)/lib/premium-gate.ts`; an unconfigured build resolves to `unavailable` and never renders purchase controls. Widening the list is a deliberate, tested change.
- Support checkout uses a STABLE idempotency key. `nextSupportConfirmation` mints one key when the reader confirms a journalist and amount, reuses it for every retry of that confirmation, and mints a new one only when the target or amount changes. A fresh key per press would dedupe nothing: the edge charges velocity and opens a provider session per new key.
- EAS pre-install guard: `scripts/check-build-env.mjs` validates store keys, backend configuration, the release manifest, controlled legal contacts, policy versions, and production smoke evidence. It LOADS `release-manifest.schema.json` and validates the manifest against it (hand-rolled walker, no new dependency), so the shape cannot drift from the checker; a test deletes every schema-required path in turn and asserts the gate fails by name. Value rules the schema cannot express live in the checker: `paymentsLive` must agree with `EXPO_PUBLIC_MYNEWS_PAYMENTS_ENABLED`/`_PROVIDER` in BOTH directions, the payment smoke checks must be true only when payments are live (a disabled rail cannot be smoke-tested), `EXPO_PUBLIC_MYNEWS_LEGAL_EMAIL`/`_SAFETY_EMAIL`/`_DMCA_EMAIL` must be controlled addresses matching `legalContacts`, and `deployAttestation.workerSecrets` must be an explicit operator attestation because backend worker secrets are invisible to an app build and the gate will not pretend to verify them.


## Accessibility contract (plan 48 WP10)

`app/__tests__/accessibility.test.ts` enforces all of this from source. These are guards against the three regressions that actually existed here, not decoration.

- **Every `TextInput` sets `accessibilityLabel`.** A placeholder is not a label: iOS reads it only while the field is empty, so the moment the user types, the field stops saying what it is. 32 of 32 are labelled.
- **Every `Pressable` / `TouchableOpacity` sets `accessibilityRole`**, and every one has an accessible name (a `<Text>` child or an explicit label). `PrimaryButton` sets its label explicitly because while `loading` the child is a spinner, and a button named only by that child announces as unlabelled at exactly the moment the user is waiting.
- **Every visual selection state ships `accessibilityState`.** A chip that looks selected but does not say so leaves a screen-reader user unable to tell which option is chosen.
- **Errors go through `components/ErrorText.tsx`, never a bare `<Text style={styles.error}>`.** All 39 error messages used to render silently: a sighted user saw them appear, a VoiceOver or TalkBack user submitting a form heard nothing, so a failed publish or a declined payment looked like nothing had happened. The component holds both mechanisms because the platforms differ: `accessibilityLiveRegion="assertive"` for TalkBack, and an explicit `announceForAccessibility` for VoiceOver, which stays silent on its own. The announce is iOS-only so Android never hears the message twice. `style` is passed through, so each screen keeps its own error styling.
- `lib/announce.ts` holds `flattenText` (pure, no `react-native` import) so it is unit-testable: the vitest suite runs in node with no RN transform, and anything importing `react-native` cannot be tested here. Put new announcement logic there, not in the component.
- **Dynamic type**: `ScreenHeader` allows two title lines (one truncates at large accessibility sizes, and the title is how the reader knows where they are). Checkbox tick glyphs use `allowFontScaling={false}` because they are decorative and sit in fixed 22pt boxes; the checked state is announced by role + state. Remaining `numberOfLines={1}` uses are deliberate list density where the full text is on the detail screen.
- **Reduced motion**: the app contains no `Animated`, `LayoutAnimation`, or reanimated usage at all, so there is nothing to reduce. A test asserts that, so the day someone adds an animation it fails and the `isReduceMotionEnabled` branch has to arrive with it. Do not add a reduced-motion no-op in the meantime.
- **Locale** is declared explicitly: `ios.infoPlist.CFBundleDevelopmentRegion = "en"` so VoiceOver picks English pronunciation rules instead of a build-machine default, and `CFBundleAllowMixedLocalizations = false` because the app genuinely ships one language. Full localization is a founder product decision.


## Expo Doctor exceptions (plan 48 WP10)

`npx expo-doctor` reports 16/18 passing. Both failures are workspace-level dependency-graph facts that cannot be fixed from inside this app, and neither is fixed by the advice Expo prints:

1. **"Duplicate native module: expo"** is a pnpm peer-resolution artifact, not a version conflict. Every copy is the *same* version (54.0.35); they differ only by pnpm peer key, because the workspace resolves two `@expo/metro-runtime` lines (6.1.2 and 55.0.9) and that forks expo's peer context. `expo-asset` therefore links a different store path for identical code. Expo's advice ("delete node_modules and the lockfile") does not change pnpm's peer keying. A native build links one expo. Fixing it properly means unifying `@expo/metro-runtime` across the workspace, which is a root-config change touching six Expo apps.
2. **`expo@54.0.35` vs expected `~54.0.36`** is a patch inside SDK 54, not an SDK upgrade. Every sibling Expo app (`mobile`, `bestchef`, `dowork`, `manhattan`, `meerkat`, `yearn`) declares a range that already permits 54.0.36, so the fix is one workspace lockfile refresh that lifts all seven together. Bumping this app alone would resolve a second expo version and make finding 1 genuinely worse.

Both belong to the root-config owner. Do not "fix" either by pinning `expo` in this app's `package.json`.
