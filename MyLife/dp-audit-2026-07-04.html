Verdict

Production readiness: 6.8 out of 10.

DoWork is much closer than the prior production review: the required test suite and parity script pass, the six edge functions exist, the main trainer/client/video/coaching routes are wired, and the prior critical queue and sign-in route regressions are mostly closed. It is not production-ready for public launch yet because several source-verified issues still break account lifecycle promises, paid entitlement timing, account switching, ended coaching relationships, workout save semantics, and some high-value mobile reliability paths.

Top 9 explicit gaps

  1. Critical: Account deletion skips dw_purchase_events, despite the App Review promise that deletion removes all server data.
  2. High: Email magic-link and password-recovery callbacks do not establish a Supabase session or complete password reset.
  3. High: Deactivated or unverified trainers are hidden from discovery but can still upload and mint playback signed URLs.
  4. High: RevenueCat CANCELLATION events revoke premium access immediately, even when current_period_end is still in the future.
  5. High: Ended client links can still receive text feedback, and failed text feedback is always presented as saved offline.
  6. High: Offline workout shares can replay under a different account after anonymous-to-email sign-in.
  7. Medium: Save Workout and Discard Workout are no-ops for title, notes, visibility, and discard intent.
  8. Medium: Continuous voice control can exhaust its restart budget during normal Android silence turnover.
  9. Medium: User-facing polish and reliability still have visible gaps: raw errors, Android keyboard behavior, dead Settings/About and workout mic rows, unvirtualized long lists, GPS chart/stats issues, and plan unsubscribe no-op.

Findings

Critical

C1. Account deletion leaves raw RevenueCat purchase events

Evidence:

  • App Review notes promise account deletion removes all server data in apps/dowork/Tickets/app-review-notes.md:50.
  • dw_purchase_events stores user_id, trainer_id, product data, price, and raw JSON in migration 20260703000001_dowork_trainer_platform_v2.sql:58.
  • dowork-delete-account deletes subscriptions, social rows, reports, videos, blocks, profiles, tokens, and storage, but not dw_purchase_events in supabase/functions/dowork-delete-account/index.ts:80.
  • The delete-account test expectation omits dw_purchase_events in supabase/functions/dowork-delete-account/__tests__/index.test.ts:83.

Failure scenario:

A user deletes their account. Auth user, visible profile, subscriptions, push tokens, and media are removed, but dw_purchase_events still retains the user UUID and raw RevenueCat payload. That conflicts with the in-app and App Review promise unless there is an explicit retention policy and anonymization.

Suggested fix shape:

Decide the policy explicitly. If deletion means deletion, remove rows where user_id = auth.uid() and consider trainer-side records where the deleting user owns the trainer. If financial audit retention is required, anonymize user_id, scrub personal fields from raw, and update App Review copy and tests to state retained purchase ledger data clearly.

Verified/refuted note:

Verified in source. This is not the deferred purchase price fallback. It is account deletion coverage.

H1. Email magic-link and password-recovery callbacks do not establish a session

Evidence:

  • Magic links and recovery emails are sent with the auth callback redirect in apps/dowork/app/(root)/data/account.ts:45 and account.ts:79.

Suggested fix shape:

Call the proper Supabase session exchange or setter through the shared client, then route only after auth.getSession() confirms the signed-in user. Add tests for magic link, recovery link, error callback, and malformed callback.

Verified/refuted note:

Evidence:

  • STATUS_BY_EVENT.CANCELLATION maps to cancelled in dowork-rc-webhook/index.ts:37, and the upsert writes that status in index.ts:185.

  • Client mirror requires subscription.status === 'active' in apps/dowork/app/(root)/data/cloud-subscriptions.ts:118.
  • Existing tests codify cancelled as inactive in cloud-subscriptions.test.ts:77.

Failure scenario:

A subscriber cancels auto-renewal with paid time remaining. RevenueCat sends CANCELLATION; DoWork writes cancelled; premium playback disappears immediately even though the user should retain access until current_period_end, unless the event is a refund or revocation.

Suggested fix shape:

Preserve access until period end. Either keep status active with a cancellation marker, or update entitlement to allow cancelled rows with a future current_period_end. Use expiration, refund, revocation, or explicit period-end events for immediate access loss. Update webhook tests, client subscription tests, subscriber count semantics, and paywall copy.

Verified/refuted note:

H5. Text feedback queues permanent rejects and tells users it saved offline

Evidence:

  • postFormFeedback queues any failed text insert if the body is non-empty and under length cap in apps/dowork/app/(root)/data/cloud-coaching.ts:623.
  • The comment says only transport-shaped failures should queue in cloud-coaching.ts:616, but no transport/permanent classification exists.

Failure scenario:

RLS rejects a feedback insert because the link ended, the participant was revoked, or the form check was deleted. The app tells the user the feedback was saved offline, clears the text, retries up to five times, then drops it.

Suggested fix shape:

Have data functions return a distinct queued result, such as { ok: false, queued: true }. Queue only known transient errors. For permanent server rejects, keep the draft, show friendly actionable copy, and do not enqueue poison items.

H6. Offline workout shares can replay under a different account

Evidence:

  • PendingShareItem stores only input, created time, attempts, and error in apps/dowork/app/(root)/data/cloud-shares.ts:89.
  • uploadWorkoutShareCore resolves user_id from the current Supabase session at replay time in cloud-shares.ts:248.
  • Queues are cleared on explicit sign-out in DoWorkCloudProvider.tsx:271, but password sign-in from anonymous state uses signInWithPassword and refreshIdentity in account.tsx:54, not sign-out.
  • Startup and foreground flushes use the current client/session in DoWorkCloudProvider.tsx:155 and :223.

Failure scenario:

An anonymous user queues a workout share while offline. Later, without explicit sign-out, they sign into an email account. The pending share lacks the enqueueing user id, so replay posts it as the email account.

Suggested fix shape:

Store the enqueueing user id on pending share items, as comments, likes, and feedback already do. On flush, post only if the current auth uid matches, otherwise hold, migrate with explicit confirmation, or drop with a local notice. Also clear or re-key all queues on auth user-id transition, not only explicit sign-out.

Verified/refuted note:

Verified for workout shares. Refuted for comments, likes, and feedback because those queues carry userId or authorUserId.

M2. Continuous voice can give up during normal Android silence turnover

Evidence:

  • Android complete silence timeout is set to 2000 ms in apps/dowork/lib/voice/useVoiceCoach.ts:87.
  • Continuous mode restarts after every end when shouldListenRef.current is true in useVoiceCoach.ts:201.
  • Restart policy allows only four restarts in a 10 second rolling window in apps/dowork/lib/voice/restart-policy.ts:10.
  • The fifth restart in that window sets handsFreeInterrupted in useVoiceCoach.ts:195.

Failure scenario:

In a quiet stretch while a video is playing, Android can emit normal silence end events every two seconds. Four normal endings inside 10 seconds use the full rapid-restart budget; the next ending stops hands-free voice and falls back to push-to-talk even though nothing unhealthy happened.

Suggested fix shape:

Separate normal silence turnover from unhealthy restart loops. Reset budget after a healthy recognition lifetime, count only rapid start/error/end failures, or use a much larger silence-turnover budget with backoff. Add policy tests for normal Android silence cycles.

Verified/refuted note:

Verified in source. This is not the prior restart oscillation bug; it is the opposite failure mode.
